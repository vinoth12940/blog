Meta Just Open-Sourced a 30B Agent That Runs Entirely on One GPU

August 26, 2026 · 9 min read · Open Source, Local AI, Agents

Muse Glimmer: a frontier teacher distilled into 30B open weights, built to run the whole agent loop on a single consumer GPU.

Every AI agent I've shipped in the last two years has had the same skeleton: a scaffolding framework wrapping a cloud model, an API key in a .env file, and a per-token meter quietly running in the background. That's the default architecture — and Meta just released a model that questions it directly.

On August 10, Meta Superintelligence Labs released Muse Glimmer: a 30-billion-parameter open-weights model distilled specifically for always-on local agent workflows. It runs on a Mac or a single consumer GPU, ships with vision input and a speculative decoder, and carries an Apache 2.0 license — which Meta describes as the most permissive license they've ever used for an open model.

The pitch in one line: the capabilities an agent actually needs — tool calling, failure recovery, long-horizon reasoning, reading screenshots — trained into a model small enough to live on your machine, with no API key and no per-token cost.

I've been running local models for years, and the gap between "runs locally" and "useful as an agent locally" has been brutal. Small models fumble tool schemas, halt on the first error, and lose the plot after a handful of steps. So I dug into Meta's research writeup, the developer docs, and — more importantly — what the local-LLM community found in the two weeks since release. The honest picture is more interesting than the launch blog.

What Muse Glimmer actually is

Muse Glimmer is a causal language model with a dedicated perception encoder, built by distilling agentic behavior from Muse Spark — Meta's larger, closed, cloud-scale model. The training pipeline has three phases, and the details matter because they explain where the model's strengths come from:

  • Pre-training on Muse Spark's outputs using logit distillation — the student learns from the teacher's probability distribution over tokens, not just its final answers, using a similar data mix.
  • Mid-training on longer-context, agent-heavy data with richer reasoning traces — the phase where the model learns what multi-step work looks like.
  • Post-training combining supervised fine-tuning with on-policy distillation and reinforcement learning across general, reasoning, coding, and agentic domains.

Meta's own capability list reads like a checklist of exactly where local agents have historically broken:

  • End-to-end task completion — evaluated on DeepSearch QA, MCP-Atlas, τ-Bench, and SWE-Bench, the benchmarks that measure whether an agent can work inside a scaffold, write and debug code, and resolve multi-turn requests start to finish.
  • Reliable tool use over long sequences — precise schemas sustained across many sequential calls, without degrading partway through a workflow. Meta calls this out explicitly: it's "the failure mode that turns a promising demo into an unreliable agent."
  • Failure recovery — when a tool call fails or returns something unexpected, the model is trained to diagnose the error and retry rather than halt. In Meta's words: "long-horizon runs are mostly a story about what happens after something goes wrong."
  • Multimodal input — interleaved text and images through the perception encoder, so an agent can read a screenshot, a chart, or a scanned document mid-reasoning.
  • Controllable reasoning effort — a reasoning_strength setting (xhigh / high / medium / low) to trade quality against speed.
  • 100+ languages in the training data, and scaffold compatibility with OpenClaw and other orchestration patterns.

That's the claim. Here's the engineering that makes it fit on your desk.

The memory story: how you fit 30B into 24 GB

Quantization does the heavy lifting — and the KV-cache headroom is where Muse Glimmer separates from same-class models on identical hardware.

At full precision, a 30B model needs over 55 GB of memory — more than any consumer GPU offers. Meta treated the memory budget as a design constraint from the start rather than an afterthought:

  • ~4-bit quantization shrinks the language model to under 20 GB. Meta validated that this compression introduces minimal to no degradation on agentic tasks, and they publish K-Quant variants — including a 17 GB build — as first-class releases, not community afterthoughts.
  • That leaves headroom inside a 24-32 GB envelope for the three things that usually get squeezed out: the KV cache (working memory), the perception encoder (vision), and the speculative decoding drafter.
  • The DFlash drafter makes it feel fast. Muse Glimmer ships with a small companion network that proposes entire blocks of tokens at once; the main model verifies them in parallel. Per Meta's numbers, that's a 3.1× decode speedup on an RTX 5090, 1.8× on M5 Max, 1.5× on M4 Max — with identical output quality, because the main model still verifies every token.

Here's the number that made the local-LLM crowd sit up. A community tester ran Muse Glimmer 30B at Q4_K_XL on a single RTX 3090: model, DFlash drafter, multimodal projector, and full F16 KV cache — configured for a 262,144-token context window in roughly 22-23 GB. Throughput: 64-124 tokens/second generation, ~1,400 tokens/second prompt processing, and it passed a two-needle haystack retrieval test at ~150K tokens on the first attempt.

Same GPU, same Q4_K_XL quantization, the same-class competition looks like this: Qwen3.6-27B tops out around 70K tokens of F16 KV context (125K only with Q8 KV compression, which trades output fidelity), and Gemma 4 31B around 52K (81K with Q8 KV). The tester who ran the comparison called Qwen's 70K limit "borderline unusable" for workflows that load whole repositories into context — and reported moving Qwen to a DGX Spark when full context was needed. That's a several-thousand-dollar jump to get what Glimmer does on a 3090.

This is the real design win: not raw intelligence per parameter, but usable context per gigabyte. For local agents that need to hold a codebase, a document set, and a long tool-call history in memory at once, that ratio is the whole game.

Now the honest part: the benchmarks

The launch-day framing and the community's framing, side by side. Both are real data.

Meta's launch materials show Muse Glimmer performing "strongly for its size class" against Gemma4-31B and Qwen3.6-27B on agentic benchmarks. But as of this writing, Meta has not published official SWE-bench, LiveCodeBench, or TerminalBench scores — so the independent picture comes from community testing, and it's more mixed:

  • TerminalBench 2.1 (multi-step terminal-agent reliability): Qwen3.6-27B at 60.7, Muse Glimmer 30B at 51.7, Gemma 4 31B at 43.4 — community-reported numbers from mid-August threads, with the caveat that TerminalBench evaluates model-plus-harness, and Qwen's official runs specify a heavily-tuned Harbor/Terminus-2 harness. The 9-point gap could narrow or widen depending on your agent setup.
  • A real coding test on an M5 Pro (48 GB): Muse Glimmer Q4 via OpenCode used ~20 GB RAM at 17 tokens/second. The tester's verdict: "overall, sits below Qwen3.6 27B" for frontend and backend work — though he noted Glimmer did not fail a single tool call during the test.
  • Token efficiency: one community benchmark author observed Glimmer is "a little less smart than Qwen, but way fewer tokens per task." No controlled study has quantified that yet — treat it as a promising lead, not a fact. But if it holds, fewer tokens per task means faster and cheaper agent loops even at slightly lower capability.
  • One report of terminal-command looping when paired with an agent framework — behavior the user hadn't seen with Qwen on the same setup. Anecdotal, configuration-dependent, but directionally consistent with the TerminalBench gap.

So the honest summary: on raw coding-agent capability, Qwen3.6-27B still leads. On hardware efficiency — context per gigabyte of VRAM — Muse Glimmer isn't close; it's a different class. Which one is "better" depends entirely on whether your bottleneck is intelligence or memory.

The gotcha that skews every bad first review

If your harness measures empty responses, you're measuring your configuration, not the model.

This is my favorite finding from the release window, because it's a trap I've hit myself with other reasoning models. Muse Glimmer is a reasoning model: before its final answer, it writes a private chain of thought to itself, and those traces are routinely multi-thousand-token affairs. If your output budget is tight, the model spends it all thinking and never emits a visible answer.

One tester's harness went from 6 of 13 tasks passing to 11 of 13 — nearly double — purely from raising max_tokens. Nothing else changed. Not the model, not the prompts, not the tools. As the writeup put it: you may be measuring your configuration, not the model.

Practical settings, assembled from Meta's docs and the community threads:

  • Give it room: Qwen's official guidance for the same class is 32,768 output tokens for general queries and 81,920 for hard tasks — a reasonable starting range for Glimmer until Meta publishes its own.
  • Stream: Meta explicitly recommends "stream": true so long reasoning generations don't hit request timeouts.
  • Tune the effort dial: reasoning_strength down to medium or low for chat-speed interactions; reserve xhigh for hard agentic work.
  • Use the chat template: always via the tokenizer's apply_chat_template, never hand-rolled — the format uses role-tagged turns with recipient markers that are easy to get subtly wrong.

Who should actually run this

After reading everything I could find, my read on the decision:

  • Run Muse Glimmer if you're building a local-first agent that needs large context on limited hardware — repository-level coding, document-heavy workflows, always-on personal assistants — or you care about privacy and offline operation as first-class requirements. The 262K-on-a-3090 result alone justifies a serious look. The Apache 2.0 license means commercial use with no negotiation.
  • Stick with Qwen3.6-27B if coding accuracy is the bottleneck and you have the VRAM headroom or multi-GPU budget. Its published benchmark base is deeper, and it leads the community TerminalBench comparison today.
  • Watch, don't switch, if you're running a production agent pipeline. Meta hasn't published official coding benchmarks yet, the harness story is still settling, and two weeks of community data is two weeks.

Getting started is genuinely one command. The weights are on Hugging Face, Ollama has it day-one (ollama run muse-glimmer), LM Studio and Unsloth ship builds, llama.cpp/ExecuTorch/MLX cover edge deployment, and vLLM/SGLang handle serving. There's even a TorchTitan path for further tuning. The Ollama page lists first-class agent integrations — including Claude Code, OpenCode, and OpenClaw launch commands.

One caveat from the community worth knowing: a single user reported the model refusing to help debug Python mouse-control code, framing it as a security concern. One anecdote, unspecified system prompt — it's not enough to conclude anything about the model itself, but if you're evaluating it for security-tooling work, test your actual use cases rather than assuming.

The bigger shift

Zoom out past this one model. The interesting thing about Muse Glimmer isn't the benchmark scores — it's what the release signals about where Meta thinks the puck is going.

The last year of open-weights releases optimized for chat quality and single-shot coding. Muse Glimmer is optimized for the tool-use loop: sustained tool calls, recovery from failure, vision mid-conversation, long context, controllable effort. Those are the components of an always-on personal agent — the thing that manages your schedule, drafts your messages, organizes your files, and, as Meta's research post puts it, "learns how you work."

An agent like that needs deep access to personal context. And there are exactly two places that context can live: on a provider's cloud, or on your machine. Meta just made the strongest open-weights argument yet for the second option — a model where the agentic behaviors are trained in rather than bolted on by a scaffold, small enough to run on hardware people already own.

It's not the smartest model in its class. It doesn't need to be. It needs to be the one that's running — locally, offline, at 3× decode speed — when you need an agent that actually finishes the job. The community will hammer on the rough edges over the coming months, and I'd bet on the harness story improving fast. But the direction is set: the agent stack is moving onto the device, and this release is the first one where I'd say the trade-offs genuinely work for real workloads.

If you've got a 24 GB GPU or a 32 GB Mac collecting dust, this is the week to ollama run muse-glimmer and see for yourself. Just remember the two rules: generous max_tokens, and streaming on.
