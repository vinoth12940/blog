Anthropic Broke Git: What 30,000 Merges a Day Means for Your Dev Pipeline

October 21, 2026 · AI / DevOps · 9 min read

Generation is machine-speed now. The wall moved to everything after it.

On October 13, Anthropic published the kind of engineering post that doesn't come along often: an admission that its own development infrastructure stopped keeping up with the code its models write. In May 2026, the company was merging around 2,500 code changes per day. By September, that number had blown past 30,000 per day. That is roughly a twelvefold increase in four months, driven by Claude Code writing the overwhelming majority of the code.

The title of this piece is a slight exaggeration — Git the protocol didn't die. But at Anthropic's scale, Git-based plumbing bent hard enough that the company did something drastic: it replaced version control entirely with an in-house system called Scion, built by a seven-person team in five months. I've spent the last week reading the post and the coverage around it, and I think it's the clearest signal yet about where the real bottlenecks in software development now live. Spoiler: they're not where they were two years ago.

The Numbers Behind the Flood

Let's get precise about what Anthropic disclosed, because the details are what make this story matter:

  • ~2,500 merges per day in May 2026 grew to over 30,000 per day by September — roughly 12x in four months, with no proportional headcount growth
  • Reporting earlier this year put Claude's share of Anthropic's merged production code above 80% — up from single digits before February 2025
  • Engineers were merging about 8x more code each day versus their pre-2025 baselines
  • Claude autonomously handled maintenance routines, filing 388 pull requests on its own — about 46% were merged after human review
  • The main branch weighs in at ~100 GB, with a compressed working copy still over 25 GB
  • CI alone performs ~25 million code checkouts per day — before counting developer environments, agent sandboxes, and research jobs

Four months from 2,500 to 30,000 merges a day — with the same headcount.

"We don't expect this rate of growth to slow down anytime soon; the latent demand for merging code is practically infinite, and every bottleneck we remove immediately leads to a further increase in the amount of code we produce." — Anthropic

That last sentence deserves a slow read. Anthropic is saying the constraint isn't ambition or headcount — it's infrastructure. Every time they remove a bottleneck, output simply rises until it hits the next one.

Why Git Couldn't Keep Up

Git's architecture assumes a world where humans are the ones committing. Every developer holds a full copy of the repository, works offline, and syncs deliberately. That model has been phenomenally successful for twenty years — but run the numbers on Anthropic's workload and it falls apart:

  • 25 million daily CI checkouts, fetched naively as full Git operations, would generate over 600 PB of traffic per day
  • Anthropic had already stacked up the standard Git survival kit — partial clones, repository snapshots, and several hundred internal mirrors — and the workarounds kept getting harder to operate as the merge rate climbed
  • Agents don't behave like offline humans. They spawn by the dozen, need fresh working state constantly, and live short lives. The distributed model's core benefit — resilient local copies — is worthless to a sandbox that exists for eleven minutes

The bottleneck had moved. Writing code was no longer the slow part. Source control, builds, and continuous integration — infrastructure designed around human development speeds — became the constraint.

Scion, in Plain Terms

So what did seven engineers build in five months? A system that quietly inverts almost every founding assumption of Git:

Scion inverts Git's founding assumptions: the server computes, the client just fetches.

  • Centralized, not distributed. Scion is a monorepo system that assumes its users — mostly agents and automated jobs — are always online. The server performs commits, merges, and history queries; clients fetch only the files they need
  • A changeset, not a commit. The unit of work is an entry in a write-ahead log that stores the list of files changed relative to its first parent, with content-addressed pointers to compressed blobs in blob storage. If that sounds closer to a database design than a Git design, that's exactly what it is
  • API-first. Source control queries are exposed as an API, so internal tools and agents can operate on the code without materializing a local repository at all

The results Anthropic reports: CPU and memory requirements 200x smaller than the Git mirroring infrastructure it replaced, checkouts for testing and research jobs about 100x faster (seconds instead of minutes), and 25% of CI's CPU capacity freed outright. Alongside Scion, the same team shipped Antique, a code review system, plus a code search tool and a source-control IAM system.

Claude itself helped build the thing that absorbs Claude's output. When an early internal version of the Mythos model became available, Anthropic had it rewrite a prototype Git-to-Scion ingestion pipeline; the result used 20 times less memory and ran four times faster than the human-written version.

"The Role of the Engineers Was to Tell Claude No"

My favorite passage in the whole post isn't about infrastructure at all. It's about what human engineers actually did during the migration:

"Very often, we found that the role of the engineers was to tell Claude 'no.' Agents will sometimes violate core system constraints to satisfy a pattern that should never have been allowed in the first place." — Anthropic

Anthropic also says the engineers who built Scion agree Claude writes better code than they do. Both things are true at once, and that's the part worth internalizing. The engineers kept architecture, design tradeoffs, and constraint enforcement. They reviewed every Scion change request, but their focus shifted from reading every line to judging the intent of the change. Nobody handed over the keys. They moved from writing every answer to designing which questions get asked.

One more operational shift stands out: at 30,000 merges a day, hundreds of changes can merge while your tests are still running, which quietly breaks the traditional merge queue. Anthropic responded by investing in testing after merge and before deployment — a reordering of the pipeline that would have sounded reckless in the pre-agent era.

The Anecdote Needs an Asterisk

Here's where I pump the brakes, because it would be easy to read this as "10x engineering productivity, just add agents." A Harvard study published days before Anthropic's post says something more uncomfortable.

The frontier anecdote and the 700-firm average agree: the constraint moved downstream.

Researchers Fiona Chen and James Stratton analyzed engineering analytics from Jellyfish — over 300 million work events across more than 700 firms and 700,000 employees, from 2021 through March 2026, comparing teams before and after AI tool adoption. Their findings:

  • AI coding agents drove +30% lines of code, +20% commits, and +23% pull requests
  • But resolution of the issues and epics those PRs feed — the actual shipped software — showed no statistically significant change
  • Review process time ballooned +49% after agents arrived; the share of PRs with changes requested nearly doubled; comments per PR rose +35%
  • The share of workers doing code review grew +14% — humans migrated downstream to absorb the flood
  • Employment didn't change significantly either way

The study's framing is that coding efficiency gains get "absorbed by downstream constraints in the production process." The authors also note that while 80% of measured firms used some form of AI code review by March 2026, agents were responsible for only about 23% of review comments — we've automated the writing of code far more thoroughly than the judging of it.

Put the two stories side by side and they don't contradict. They're the same curve at two points. Anthropic removed bottleneck after bottleneck and kept finding more — because each removal just fed the next stage harder. The Harvard data shows what happens to the 700 firms that haven't rebuilt their plumbing yet: the agent writes the code in an afternoon, and it ages three weeks in a human review queue.

This Is Bigger Than One Lab

If Anthropic were alone in this, it'd be a curiosity. It isn't:

  • GitHub itself published a post in April attributing recent platform availability problems to exponential growth in pull requests and commits — the code flood is stressing the world's largest forge
  • Cursor launched Origin into early beta in August, rebuilding the developer workflow around agents — editor, cloud agents, stacked PRs, merge queues — while keeping Git as the wire protocol
  • The precedents were already there: Google's Piper monorepo, Meta's Sapling, and Microsoft's VFS for Git all attacked pieces of this scaling wall for humans. What's changed is that the pressure now comes from machines, at machine volume

Anthropic, to its credit, is explicit that Scion is not a general-purpose Git replacement, suits only enormous repositories with large agent populations, and won't be open-sourced. Analysts watching this space mostly agree: Git isn't going away — the Git client is what's getting demoted, from the center of the stack to a compatibility layer, while the value moves to the server.

What I'd Actually Do About It

Most teams reading this will never merge 30,000 changes a day, and Anthropic's own caution applies: don't rip out Git because a frontier lab did. But the direction of the bottleneck is the same at every scale, just smaller. If you're running coding agents against a real codebase, this is where I'd look:

  • Measure review throughput, not code output. Lines generated is a vanity metric now. The number that predicts delivery is time-from-PR-open to merged — and if it's growing after agent adoption, you've found your wall. The Harvard data says most teams have
  • Point agents at the review queue, not just the editor. With 80% of firms using AI review but agents writing only a fraction of review comments, triage-and-first-pass automation is the most underexploited lever. The 49% review-time inflation is the tax you're paying for not doing it
  • Make the pipeline agent-native where it's cheap. Ephemeral workspaces instead of full clones, API-first tooling, pre-primed caches, checkout time as a tracked metric. You don't need Scion to notice that a 40-minute CI checkout is hostile to an agent that lives for eleven minutes
  • Encode constraints instead of repeating them. Anthropic's "tell Claude no" lesson scales badly as a human job. Write the constraint into lint rules, CI gates, and architecture tests, so the agent hits the guardrail without a human in the loop
  • Think about post-merge testing now. If your merge rate doubles, merge queues jam first. Testing after merge and before deployment is how the highest-volume shop on the planet coped — worth designing for before you need it
Code generation became the cheap part almost overnight. Everything after the commit is where the engineering went — and where it's going.

The Scion post will probably be remembered as the moment version control joined the list of things AI loudly outgrew. But the more useful takeaway is quieter: Anthropic is the first to publish the numbers from the other side of the wall, and the numbers say the wall didn't disappear. It moved. Your stack has a wall like that too — it's just measured in hours of review queue instead of petabytes of checkout traffic. Go find it before your agents do.
