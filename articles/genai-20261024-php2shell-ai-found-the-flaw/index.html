PHP2Shell: How AI Turned a Decade-Old PHP Flaw Into a Global Emergency

October 24, 2026 · AI / Security / Self-Hosting · 9 min read

The flaw was always there. AI changed what it costs to use it.

This was the week the NSA told websites to turn themselves off. More than thirty UK government services went dark, alongside Dutch, German, Belgian and French federal portals — all preemptively, all because of two bugs in PHP, the language that powers roughly 70% of the websites whose server-side language we know. Cloudflare watched exploit attempts climb from thousands before the announcement to millions within a day. Security researchers started calling it Black October.

The vulnerabilities got a name that sounds like a movie title: PHP2Shell. Two memory-safety flaws, CVE-2026-109618 and CVE-2026-109619, sitting in PHP's core request handling — a language I run on my own self-hosted stack, and probably one you run somewhere too. But the part of this story I can't stop thinking about isn't the vulnerability itself. It's who found it, how, and what it means that the exploit only became practical this year.

Because here's the thing: those flaws had been in the PHP codebase for more than a decade. What changed in 2026 wasn't the code. It was the economics of turning it into a weapon.

What PHP2Shell Actually Is

Strip away the name and this is a class of bug as old as C itself: memory-safety failures triggered when a PHP request dies mid-flight. Wiz Research, which published the deepest technical writeup, traced all of them to how PHP handles fatal errors — especially out-of-memory errors — while processing requests.

The pattern goes like this. An out-of-memory condition interrupts PHP while internal request data is only partially initialized. The cleanup never finishes, and the worker process is left with global state — things like the session ID pointer or unserializer bookkeeping — that still points at memory that has been freed. The worker survives and serves the next request. If an attacker can craft a request that lands on that poisoned worker and gets their own data written into the freed region, PHP will happily treat attacker-controlled bytes as live internal state. From there it chains to memory corruption and, ultimately, code execution.

Wiz demonstrated the full chain — branded php2shell as a single exploit script — against the latest container images of WordPress, Drupal, and Joomla: unauthenticated remote code execution with a single request, before any application code runs. They also demonstrated a quieter variant: application-agnostic memory disclosure that leaks passwords, tokens, and API keys from other users' requests, encoded into a malformed PHPSESSID cookie. Even a "Hello World" app on a vulnerable PHP version was exposed, because the flaw isn't in the application layer at all.

One dead request poisons the worker. The next request walks in.

  • Two CVEs, CVSS 9.2 — every PHP release of the last decade is affected by at least one of them, going back to PHP 5.4
  • Every SAPI exposed — PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, LiteSpeed; mod_php deployments face the greatest danger
  • Decade-old code — the underlying bugs predate the modern AI era entirely; several variants beyond the two CVEs were found during coordination
  • Fixed in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35, released October 21, 2026
"These findings rank among the most severe vulnerabilities discovered in PHP, and arguably in software history. The underlying flaws had been present for decades, but demonstrating their exploitability required an exceptionally complex chain of steps, at the edge of what human researchers could practically achieve. Frontier AI models substantially reduced that barrier, turning a longstanding flaw into an exploit." — Wiz Research

The AI Part: From Dormant to Weaponized in a Week

When the cost of exploitation collapses, every "hard to exploit" CVE needs re-pricing.

Here's the timeline that matters. On August 11, the security firm Calif discovered the vulnerability class while working through OpenAI's "Patch the Planet" initiative. A week later, on August 19, Wiz Research independently found it — using their Wiz Atlas autonomous vulnerability-research system running Gemini 4 Argon and GPT-5.6 Sol, with Wiz noting that Argon made a particularly significant contribution. By August 20 they had unauthenticated RCE against Drupal. By August 21, WordPress. That's two days from "the bug exists" to "the bug is a weapon" — for flaws that had sat harmless for ten years.

The gap between those two facts is the whole story. Turning these bugs into a working exploit required chaining multiple memory-corruption primitives and adapting to each target's memory layout — PHP version, distribution, container base image, all of it. Pre-AI, that was specialist work measured in months. Wiz's conclusion, stated plainly: a single researcher with frontier models and the right tooling completed in a week what previously would have taken a world-class team months. OpenAI's own team called it "one of the most impactful vulnerabilities in recent memory."

And the same capability cut both ways. Chainguard, the container-distribution company, independently rediscovered the vulnerability in a single evening using an in-house AI harness and a frontier model, once they heard a disclosure was coming — which should tell you exactly how reproducible this class of AI-assisted discovery has become.

Sixty Days of Silence, Then the Leak

Sixty days of quiet coordination, then seventy-two hours of chaos.

The coordination itself was a genuinely impressive cross-industry effort: Calif, Wiz, OpenAI, the PHP Foundation, plus Automattic, Akamai, AWS, Cloudflare, Fastly, Google, Imperva, Microsoft and Vercel preparing mitigations. Patch day was planned for Thursday, October 22.

Then the plan met reality, in public:

  • October 17: Amazon's MadPot honeypot network recorded the first exploitation attempts — four days before public disclosure, from an anonymized address AWS assessed as a real threat actor. How they learned about the bug early is still unknown.
  • October 20: CVE identifiers started circulating on forums. Vulnerability hunting and proof-of-concept attempts erupted across the internet. Worse, Calif accidentally published a PoC video demonstrating the exploit against active targets — quickly deleted, widely copied.
  • October 21, 07:41 UTC: With European PHP maintainers asleep and multiple vendors reporting active exploitation overnight, Chainguard published container images containing the fix — more than six hours ahead of the coordinated release.
  • October 21: The PHP maintainers pulled the patch release forward a day and shipped 8.5.12, 8.4.27, 8.3.36 and 8.2.35. Public disclosure followed.

The Foundation did not mince words about Chainguard: "Any attacker could now study the fix in binary form while every other PHP user was still waiting for the release." Chainguard's CEO, Dan Lorenc, defended the call — the builds were public, not customer-gated, and he judged evidence of in-the-wild exploitation sufficient to justify breaking the embargo. Both positions are defensible. That's exactly what makes this the most instructive disclosure fight in years: the old coordinated-disclosure playbook assumes humans reverse-engineering patches take days. AI-assisted attackers take hours. The playbook needs a rewrite, and this incident is the case study everyone will cite.

How Bad Is It, Really?

The exploitation numbers are genuinely alarming, and the breach count is genuinely zero. Both are true, and the gap between them is worth understanding.

"In the 10 hours before it was publicly announced, across the Cloudflare network we saw thousands of attempts to exploit it. That jumped to tens of thousands in the 45 minutes post-announcement, hundreds of thousands within two hours, and millions now." — Matthew Prince, Cloudflare CEO

Hadrian reported PHP2Shell being exploited "in the wild at scale" within a day, with most observed attacks abusing PHP's session upload-progress mechanism. VulnCheck reproduced both bugs and found working RCE possible on ARM64 systems — where ASLR can be brute-forced relatively easily — and on x86 without ASLR. Dozens of PoC repositories appeared on GitHub.

And yet, as of October 23, the PHP Foundation's Elizabeth Barron stated there was no evidence of successful exploitation prior to disclosure, and none against patched systems. The Register polled multiple security researchers and got the same answer: attempts everywhere, confirmed breaches nowhere. Mandiant's CTO Charles Carmakal offered the most useful technical read: most public PoCs "appear to be 'vibe-coded' and are incapable of remote code execution," though his team validated some that work against default mod_php deployments. This is a genuinely hard exploit — environment-specific, sensitive to memory layout — and that difficulty is the only reason a bug this severe produced millions of attempts and zero confirmed casualties. We got lucky that it's hard.

One more wrinkle: on October 23 the Foundation reserved a third CVE, CVE-2026-115560, but declined an emergency fix because it requires an unlikely configuration combination — and published a one-line mitigation: set session.upload_progress.enabled=0.

If You Run PHP — and You Probably Do

Five moves in order — patching is the only complete fix; everything else buys time.

Every PHP installation that serves web requests is affected. If you self-host — WordPress, Nextcloud, a NAS web stack, anything with a .php file in it — here's the priority order I'd actually follow:

  • Patch first. PHP 8.5.12, 8.4.27, 8.3.36, or 8.2.35. If you're on 8.1 or older, you're past upstream end-of-life — check your distro for backported fixes or upgrade now. On shared hosting, verify your provider's PHP version before you assume you're fine; DreamHost and other hosts pushed fixes network-wide, but nobody should be guessing.
  • Can't patch? Go dark. This sounds dramatic, but the NSA's Cybersecurity Collaboration Center and the UK's NCSC both advised it, and thirty-plus government services proved it's the realistic option. Isolate the box from untrusted networks until you can update.
  • Buy time with config. Setting session.upload_progress.enabled=0 kills the primary attack path used by most observed attacks. Reverse-proxy limits on request size, multipart fields, and nesting depth reduce exposure further. None of it substitutes for the patch.
  • Hunt for the signs of trying. Wiz's guidance: unusual multipart requests followed by memory-limit errors or repeated HTTP 500s, unexpectedly large or malformed PHPSESSID cookies, unexplained PHP worker churn. Remember these bugs run below the application layer — your app logs may show nothing.
  • Audit the appliances. Palo Alto confirmed all PAN-OS and Panorama versions affected, with no fix at disclosure time; Cisco was still investigating 18 products and 13 cloud services; press coverage flagged NAS vendors with PHP bundled and no patch yet. The long tail here is embedded stuff that never gets patched — as forensics expert Hal Pomeranz put it, "there will be a long tail for this one."

Black October, and What Changes Now

PHP2Shell didn't happen in isolation. The same fortnight produced critical AI-found flaws in Node.js, Plex, and enterprise Java stacks; OpenAI cut off internet access during model training; a red-team report dinged OpenAI's agent monitoring. NPR's Kevin Roose, who interviewed researchers all week, summarized where this is heading: for the next year or two, "every week is going to feel like a new crisis" as AI systems crawl over decades of accumulated software and probe what's broken.

"We may have much more secure systems once all these bugs have been fixed... but right now, this is crunch time for people who worry about cybersecurity." — Kevin Roose, NPR

Wiz compared PHP2Shell to Heartbleed and Log4Shell — the moments that redefined how we think about shared infrastructure risk. I think the comparison undersells it, in one specific way: Heartbleed and Log4Shell changed how we inventory dependencies. PHP2Shell changes how we should think about severity itself. "Hard to exploit" used to be a meaningful defense. It meant years, or a world-class team, or luck. When a skilled researcher with frontier models can compress that into a week — and vendors can independently rediscover a secret bug in an evening — then complexity stops being a security boundary and becomes just a speed bump with better funding. Every CVSS score with "requires a complex exploit chain" in its vector needs re-pricing, because the cost side of that equation just fell off a cliff.

The honest ending is that this cuts both ways. The same models that built the exploit in days also helped build, verify, and distribute the fix — and the discovery itself is a win: three independent teams found a decade-old flaw that generations of human review missed, and the internet patched it in 72 hours with zero confirmed breaches. That's the deal AI is offering security teams in 2026: your attackers get faster, and so do you, and the difference between catastrophe and a bad week is which side of the patch you're on when the crawl reaches your server.

I spent Wednesday evening updating PHP on my own boxes and checking appliances I'd honestly forgotten ran PHP. It took twenty minutes. If you haven't done yours yet — that's the action item. The crawl is already running.
