The NEAR AI Breach Proves Your Inference Server Is the Attack Surface

November 11, 2026 · AI / Security / Self-Hosting · 8 min read

One RCE bug, one server, three compromised systems. The full verified path from NEAR AI's own forensics.

While most of the industry spent the weekend watching election fallout and earnings, an attacker was busy. On Sunday, November 8, they exploited a remote code execution vulnerability in SGLang — one of the most widely deployed open-source LLM serving engines — and got code execution on an inference server run by NEAR AI, the confidential-computing cloud whose entire pitch is that your prompts are private even from the company operating the hardware. By Monday, NEAR AI had published a full incident report. Everyone involved moved fast. It didn't matter, because the bug was faster.

I've spent this year covering AI security incidents as they happen — the OpenClaw crisis, agents hacking government sites, the ARTEX agentic attack wave, GPT-6 Cyber going commercial. This one is different, and it's the one I'd most want any self-hoster to read. Because the detail that matters isn't the breach itself. It's this: requests sent in confidential mode — inside a hardware trusted execution environment — were among what the attacker could observe. The enclave did exactly what enclaves do. The software running inside it did exactly what buggy software does.

What Actually Happened

NEAR AI's incident report, published November 9, lays out the path with unusual precision. The attacker exploited an RCE vulnerability in SGLang to execute code on one inference server. From that single foothold they moved laterally into internal systems. There they reached the backend of Private Chat — a product NEAR AI had already deprecated — and downloaded account details for approximately 100 users: email addresses, names, and for some accounts, plan and balance information. They reached an older deployment of NEAR AI Agents that ran outside the confidential computing environment, and pulled data from 18 agents: chat history, settings, and logs. And in the detail that should sting every operator: two customers' API keys were sitting in logs on the compromised systems. Both were revoked.

Small numbers by breach standards — but every line item is a lesson in what AI infrastructure leaks first.

  • November 8, 2026 — attacker exploits an SGLang RCE on one inference server; requests in processing that day, including confidential-mode requests, were observable
  • ~100 users — account details (email, name, plan/balance for some) downloaded from the deprecated Private Chat backend
  • 18 agents — chat history, settings, and logs taken from a legacy deployment that ran outside the TEE
  • 2 API keys — customer cloud keys found exposed in logs; both revoked
  • Not accessed — stored Private Chat conversations and uploaded files, per NEAR AI's forensics
  • November 9 — public incident report published; fix deployed across all inference servers; service restored
"We have found no indication that stored Private Chat conversation or uploaded files were accessed." — NEAR AI incident report, November 9, 2026

The TEE Paradox

Here's the part that should reframe how you think about confidential computing. NEAR AI's product is built on trusted execution environments: hardware enclaves where inference runs in encrypted memory, attested remotely, so that not even the operator can read your prompts. Brave's Leo assistant runs chats this way on NEAR AI's infrastructure — verified by Brave itself, disclosed in October. Confidential inference is a real product category with real adoption, and NEAR AI is one of its most visible implementations.

And then one of the most consequential sentences any vendor has published this year, in a post written about their own breach:

"Confidential computing protects data from the operator and the host. It does not protect against a vulnerability in the software running inside the environment, and that is what happened here: the SGLang vulnerability let the party run code inside one inference server and access requests in processing on that server, including confidential ones." — NEAR AI

The enclave guards against every adversary outside the box. A bug in the code inside the box is not one of them.

Think about what a TEE actually is: a hardware fence around memory. If the application inside the fence contains a flaw that hands control of that application to an attacker, the fence is now around the attacker. Memory encryption protects the prompt from a curious cloud admin or a stolen memory snapshot. It does nothing whatsoever about pickle.loads() on a socket that accepts unauthenticated input. Confidential mode is a boundary upgrade — a genuinely valuable one — but it sits orthogonal to the security of the serving stack, not above it.

SGLang Is Everywhere, and Its Advisory Record Was on the Wall

SGLang is not a niche tool. It's a high-performance serving framework for large language and multimodal models with roughly 38,760 GitHub stars and thousands of production deployments — the engine you spin up when you want fast, batched inference without hand-rolling a serving layer. If you self-host models, there's a decent chance you run it, or something shaped exactly like it.

Which is why the advisory record matters. As of November 11, the OSV database lists 20 published vulnerabilities for the project — and several of them are unauthenticated remote code execution with a single repeating root cause: Python deserialization of untrusted data on network-reachable sockets.

  • CVE-2026-3059 — unauthenticated RCE via the multimodal generation module's ZMQ broker, which deserializes untrusted data with pickle.loads() and no authentication. Fixed in 0.5.10.
  • CVE-2026-3060 — unauthenticated RCE via the encoder parallel disaggregation module, same pickle.loads() pattern. Fixed in 0.5.10.
  • CVE-2026-7304 — unauthenticated RCE when the custom logit processor flag is enabled: Python objects loaded via dill.loads() with no validation. Affected versions through 0.5.12.
  • CVE-2026-7301 — the multimodal scheduler deserializes untrusted pickle on a socket bound to 0.0.0.0.
  • CVE-2026-7302 — unauthenticated path traversal in the multimodal generation runtime.
  • CVE-2025-10164 — RCE via unsafe deserialization in the update_weights_from_tensor path.

The bug class that breached NEAR AI had six published predecessors. The pattern was on the wall since March.

Distributed ML serving frameworks lean heavily on Python's object serialization to move tensors, weights, and config between processes and nodes — and pickle and dill will happily execute code during deserialization. Every one of those sockets is an RCE waiting for someone to expose it to the wrong network. This is not an SGLang pathology alone: vLLM, the other dominant open serving engine, has 194 advisories in the same database, including RCE-class findings like CVE-2026-22807 (dynamic module loading during model initialization) and CVE-2024-11041 (deserialization of untrusted data). The serving layer of the AI boom is built on a deserialization habit that security teams spent the last decade stamping out of every other Python service.

Now for the uncomfortable part: the specific flaw used against NEAR AI still has no public name. As of this writing, there's no CVE number, no affected-version range, and no project advisory — NEAR AI says it deployed a fix across its fleet and reported the vulnerability to the SGLang project, but the public disclosure hasn't landed. If you run SGLang today, you cannot yet check whether you're vulnerable by version number alone. That gap between "vendor knew and patched" and "the world can verify" is exactly where the next attacker operates.

Credit Where the Response Is Due

Before the lessons, some earned praise. NEAR AI detected the intrusion, revoked every active session and administrative credential, replaced all agent tokens, took the deprecated product offline, deployed the fix across all of its inference servers, completed credential rotation and a full forensic review, restored service, and published a plain-language incident report — all inside roughly a day. Affected users were contacted directly, with a follow-up telling everyone else they need do nothing. And the report is honest about the limits of the company's own core technology, which is rarer than any of the containment metrics.

"We are now treating the inference software and the services around the enclave with the same rigor as the enclave itself when running security analysis." — NEAR AI

That last line is the whole industry's homework in one sentence. The confidential-computing stack spent years hardening the enclave. The software that runs inside it — and the deprecated products and log pipelines around it — clearly didn't get the same budget. NEAR AI noticed. The question is whether every other confidential-inference vendor, and every homelab running the same engines, notices without needing their own incident to learn it.

The Self-Hoster's Hardening Checklist

Everything above maps to concrete moves you can make this week, whether you're running one Ollama box for a household or a small vLLM/SGLang fleet for a product. Seven layers, in order of how fast they pay off:

Seven layers, each mapping to something that actually failed at NEAR AI — or would have stopped it earlier.

  • Treat the inference server as internet-facing — even on your LAN. Never port-forward Ollama, vLLM, or SGLang through your router or a tunnel. One misconfigured tunnel is all the exposure an unauthenticated RCE needs, and browser-reachable LANs have their own request-forgery paths.
  • Pin the engine version and actually watch its advisories. SGLang's unauthenticated RCE class was fixed in 0.5.10, published in March. If you're below that, you're running the NEAR AI bug class today. Subscribe to the project's GitHub security advisories or an OSV feed — patch cadence on your inference engine is now a security control, not hygiene theater.
  • Disable deserialization-hungry features you don't use. Custom logit processors, weight-update endpoints, multimodal pipelines, ZMQ ports. CVE-2026-7304 required an opt-in flag. If a feature moves Python objects over a socket and you don't need it, turn it off.
  • Bind RPC and management ports to localhost — never 0.0.0.0. One SGLang advisory literally names a socket bound to 0.0.0.0. Internal components become internet services one config line at a time.
  • Keep secrets out of logs. Two NEAR AI customers lost API keys to log files. Scrub keys and tokens from your log pipelines before the incident, and rotate anything that ever touched a host you don't fully trust.
  • Deprecated means deleted. The lateral movement went through a product NEAR AI had already retired but was still running. Anything still up is still attack surface — old deployments are the soft entry point in almost every modern breach.
  • Confidential mode is a boundary upgrade, not a patch substitute. Enclaves protect your prompts from the operator. They do not protect a vulnerable app from itself. Patch first, enclave second — and never let the enclave's marketing become your threat model.

What to Watch Next

Three things I'm tracking. First, the SGLang project's public advisory — when it lands with a CVE and a version range, check your deployment the same hour. The gap between private fix and public disclosure is where copycat attacks live, and the NEAR AI report has now advertised that this bug exists. Second, whether confidential-inference vendors respond structurally — NEAR AI has committed to treating the serving layer with enclave-level rigor, and its stack is public so the claim is verifiable; watch whether others follow or wait for their own incident. Third, the Brave Leo question — Brave confirmed its assistant runs private inference on NEAR AI's enclaves, and neither company has said whether the affected server handled any of those chats. Consumer privacy infrastructure is now one deserialization bug deep in the same story.

The uncomfortable summary: a vendor whose entire product is hardware-enforced privacy got breached through the software running inside the hardware, and the response proved the theory I keep returning to in these articles — the fence is only as good as the code inside it. Hardware trust doesn't patch software. If you self-host models, your serving engine is now the most interesting machine in your stack. Treat it that way before someone else demonstrates it for you.
