I Gave My AI Agent Eyes on a Headless Linux Server

May 12, 2026 · Vinoth · 8 min read · Hermes Agent, Linux, Computer Use

Running an AI agent on a headless server is great until the agent needs to see something.

My Hermes Agent lives 24/7 on a Minisforum UM760 Slim with an AMD Ryzen 5 7640HS, 16GB RAM, and Linux Mint 22.3. It is my always-on home server. It can run commands, edit files, browse the web through tools, and answer from Telegram. But when a task needed a real desktop, the story ended quickly: no monitor, no GUI, no display.

Hermes already has a built-in computer_use tool. The problem was that it only worked on macOS because the existing backend uses cua-driver, which relies on macOS-only SkyLight private APIs. On Linux, the tool was simply unavailable.

I did not want a theoretical demo. I wanted every Hermes session on my Linux server to have a real 1280x720 desktop it could screenshot, click, type into, and debug visually when needed.

The bridge: Hermes talks HTTP, the container provides a real XFCE desktop.

The Dead End

The original Hermes path is clean on macOS: call the computer_use tool, load the CuaDriverBackend, and let cua-driver control the desktop.

That path does not exist on my server. Linux Mint on a headless box has no native SkyLight API, no attached display, and no GUI session waiting for an agent. The useful part of Hermes was already running perfectly, but the one feature that needed pixels was locked to another operating system.

The constraints were simple: keep macOS unchanged, keep Linux local to 127.0.0.1, use a real desktop, and make it survive reboots.

The Idea: A Desktop in Docker

The solution was trycua/cua, specifically the CUA XFCE Linux container. It packages an XFCE desktop with a REST API for computer-use actions. It also exposes noVNC on port 6080, which is useful when I want to see what the agent is seeing.

The container I used is trycua/cua-xfce:latest. The image is 5.66GB, the REST API listens on http://127.0.0.1:8000, and the desktop resolution is fixed at 1280x720.

docker run -d --name cua-desktop --restart unless-stopped \
  -p 127.0.0.1:8000:8000 -p 127.0.0.1:6080:6080 \
  -e RESOLUTION=1280x720 trycua/cua-xfce:latest

That command gives Hermes a full XFCE desktop, REST endpoints for actions, and a noVNC debug window on 127.0.0.1:6080.

The Implementation

I added a new file: tools/computer_use/http_backend.py. It is 218 lines, 8.5KB, and defines CuaHttpBackend, a Linux-friendly backend that inherits from Hermes' existing ComputerUseBackend interface.

The backend uses a reused requests.Session, a 30-second timeout per API call, and the container's /cmd endpoint. The CUA server returns SSE-style responses like data: {...}, so the backend also strips that wrapper before parsing JSON.

The backend shape

class CuaHttpBackend(ComputerUseBackend):
    """Drives a CUA XFCE container via its REST /cmd endpoint."""

    def __init__(self, url: str = _DEFAULT_URL) -> None:
        self._url = url.rstrip("/")
        self._session = requests.Session()

    def is_available(self) -> bool:
        try:
            r = self._session.get(f"{self._url}/status", timeout=5)
            return r.status_code == 200 and r.json().get("status") == "ok"
        except Exception:
            return False

The methods mirror the normal computer-use contract: start(), stop(), is_available(), capture(), click(), type_text(), key(), drag(), scroll(), list_apps(), and focus_app().

The SSE parser

def _cmd(self, command: str, **params) -> Dict[str, Any]:
    """Send a command to /cmd and parse the SSE response."""
    payload = {"command": command}
    if params:
        payload["params"] = params
    r = self._session.post(
        f"{self._url}/cmd",
        json=payload,
        timeout=_TIMEOUT,
    )
    r.raise_for_status()
    text = r.text.strip()
    # Handle SSE "data: {...}" wrapper
    if text.startswith("data: "):
        text = text[len("data: "):]
    # Sometimes multiple lines
    for line in text.split("\n"):
        line = line.strip()
        if line.startswith("data: "):
            line = line[len("data: "):]
        if line.startswith("{"):
            return json.loads(line)
    raise RuntimeError(f"Could not parse response: {text[:200]}")

The fallback in Hermes

The second change was in tools/computer_use/tool.py. The key is that macOS still gets first chance. If cua-driver imports and starts, nothing changes. If it fails, Hermes tries the HTTP backend. I can also force the HTTP backend with HERMES_COMPUTER_USE_BACKEND=http.

def _get_backend() -> ComputerUseBackend:
    global _backend
    with _backend_lock:
        if _backend is None:
            backend_name = os.environ.get("HERMES_COMPUTER_USE_BACKEND", "cua").lower()
            if backend_name in {"cua", "cua-driver", ""}:
                try:
                    from tools.computer_use.cua_backend import CuaDriverBackend
                    _backend = CuaDriverBackend()
                except Exception:
                    # cua-driver (macOS) not available — fall back to HTTP
                    from tools.computer_use.http_backend import CuaHttpBackend
                    _backend = CuaHttpBackend()
            elif backend_name in {"http", "cua-http"}:
                from tools.computer_use.http_backend import CuaHttpBackend
                _backend = CuaHttpBackend()
            elif backend_name == "noop":  # pragma: no cover
                _backend = _NoopBackend()
            else:
                raise RuntimeError(f"Unknown HERMES_COMPUTER_USE_BACKEND={backend_name!r}")
            _backend.start()
        return _backend

I also changed check_computer_use_requirements() so Linux returns True when the container API is reachable. That is what makes the computer_use tool show up in Hermes sessions instead of disappearing on Linux.

The fallback is intentionally boring: native macOS first, HTTP container backend only when needed.

Wiring It Into Production

A desktop container is only useful if it is actually running when the agent needs it. Docker's --restart unless-stopped handles host reboots, and I added a health check to my maintenance.sh, which runs every 5 minutes from crontab.

# Check CUA Desktop Container (Docker, port 8000)
CUA_RUNNING=$(docker ps --filter name=cua-desktop --format '{{.Status}}' 2>/dev/null)
if [ -z "$CUA_RUNNING" ]; then
    log "[WARN] cua-desktop container is NOT running. Starting..."
    docker start cua-desktop >/dev/null 2>&1 || \
        docker run -d --name cua-desktop --restart unless-stopped \
            -p 127.0.0.1:8000:8000 -p 127.0.0.1:6080:6080 \
            -e RESOLUTION=1280x720 trycua/cua-xfce:latest >/dev/null 2>&1
    sleep 3
fi

CUA_HEALTH=$(curl -s --connect-timeout 3 http://127.0.0.1:8000/status 2>/dev/null || echo "")
if echo "$CUA_HEALTH" | grep -q '"ok"'; then
    log "[OK] cua-desktop container is healthy"
else
    log "[WARN] cua-desktop API not responding — restarting"
    docker restart cua-desktop >/dev/null 2>&1
fi

The important part is the two-layer recovery:

  • Container down: start the existing container, or create it if it does not exist.
  • Container running but API unhealthy: restart the container and check again.

What I Will Actually Use It For

This is not about letting an agent randomly click around my server. The value is in the stubborn tasks that do not fit cleanly into shell commands or headless browser automation.

  • Medium publishing: Medium import and editor flows are visual, stateful, and often hostile to pure headless automation.
  • Visual QA: when I generate articles, dashboards, or diagrams, the agent can inspect the rendered page instead of only reading the source.
  • Web automation edge cases: some workflows need a real desktop session, not just HTTP requests or a browser DOM.

For normal automation, I still prefer APIs, scripts, and deterministic tools. The desktop is the fallback for the places where the web is messy.

Lessons Learned

The surprising part was not the Docker container. That worked cleanly. The tricky part was making the integration feel native to Hermes without breaking the macOS path.

  • Backward compatibility matters: the safest patch was a fallback, not a replacement.
  • Availability checks are product behavior: if check_computer_use_requirements() says False, the tool effectively does not exist for the agent.
  • Health checks are not optional: an always-on agent needs boring maintenance more than clever demos.
  • SSE wrappers are easy to miss: the API response looked like JSON, but it arrived wrapped as data: {...}.

This is a bridge, not a claim that Hermes has native Linux computer use. The bridge depends on the CUA XFCE container being installed, running, and reachable locally.

What Is Next

I opened GitHub issue #15876 on NousResearch/hermes-agent to propose native Linux computer use support. The issue was created on April 26, 2026 and is still open.

Once Hermes adds native Linux support, I will revert the custom code. Until then, this container bridge gives my headless home server something it never had before: eyes.

And for my day-to-day use, that is enough. Hermes can keep running on Linux Mint, stay online 24/7, and now, when the job demands a desktop, it can finally look.
