40% of All GitHub Pull Requests Now Start With an AI Agent

October 31, 2026 · AI / DevOps / Open Source · 8 min read

Six months from curiosity to near-half of the world's largest code platform.

Last Tuesday at GitHub Universe, Satya Nadella put a number on stage that I haven't stopped thinking about: more than 40% of all pull requests on GitHub now start with an agent's first draft. Six months ago that share was 17%. The raw volume of agent-drafted PRs grew roughly sixfold over the same period. This isn't a forecast, and it isn't a survey of what developers say they'll do — it's what actually happened on the world's largest code platform, measured across 225 million developers.

I run agentic workflows myself. An agent on a headless Linux server in my closet drafts, checks, and ships posts to the blog you're reading. For the past year that has been a hobbyist curiosity. GitHub's Octoverse 2026 report, published October 28, says it is now the default way software gets made. The numbers deserve a close look — and so do the caveats.

The Numbers Behind the Headline

The Octoverse year — the twelve months to September 30, 2026 — set records everywhere GitHub measures:

  • More than 40% of pull requests began as an agent's first draft in September — up from 17% in March
  • 17.9 billion pushes — more than 2024 and 2025 combined
  • 34.3 billion commits — more than three times the level two years earlier
  • 1.3 billion merged pull requests — an average of 3.5 million every single day
  • 1,440 GitHub Actions jobs per second, around the clock
  • 225 million developers on the platform — 38.3M in the US, 32.0M in India
  • 2.5 billion public contributions — more than double 2025's total of 1.12 billion

Any one of these would have led a slow news week. Together they describe a different shape of software work.

September alone saw roughly 110 million pull requests opened. The arithmetic is worth pausing on: at 3.5 million merges a day, human typing alone no longer explains the volume — and GitHub's own data says as much, with agents drafting the first version of nearly half of it. On the adoption side, 55% of monthly active Copilot users now use agentic features, up from 35% a year ago, and cloud-based agents that run tasks remotely grew 230% year over year.

The Part Nobody Predicted: Agent PRs Merge Faster

Here's the stat that surprised me most, and it isn't the 40%. It's how agent-drafted PRs perform in review.

Bigger diffs, faster merges. The machine-drafted changes are not the small ones.

Agent-involved pull requests changed multiple files 87% of the time, versus 79% for traditional PRs. And as of September, 90% of agent-drafted PRs merged within two weeks, versus 86% for traditional ones. Read that twice: the machine-drafted changes are larger, and they clear review faster than the human-only ones.

My read of why: the popular image of agent PRs as typo-fix drive-bys is wrong. Given a ticket, an agent takes the whole ticket. And a PR that arrives pre-scoped, with a clean description, tests included, and CI already green is simply easier to say yes to. There is selection bias all over this stat — teams that enable agents also redesign their work into smaller, well-defined units — and GitHub doesn't claim causation anywhere. But the direction is hard to argue with.

The tell isn't that agents open more pull requests. It's that humans merge them — faster than the ones we write ourselves.

The 8x Repo: What Agent-Ready Actually Means

The stat with the most practical payoff barely made headlines. Among repositories created in 2026, those that included an agent configuration file averaged eight times more commits than those without one.

The report itself flags the obvious caveat: correlation, not proof of cause. Teams that bother writing an AGENTS.md are probably the teams shipping hard anyway. But the mechanism is real no matter how you discount the multiplier. An agent config file is house rules for a contributor who never sits in your onboarding sessions: it removes guesswork about how to build, how to test, and where the guardrails are. If a new engineer needs it, an agent needs it more.

Five layers, four of which are free GitHub features you can enable today.

What actually goes in the config file, from my own repos:

  • Build and test commands — the exact incantations, so the agent verifies instead of guessing
  • Code conventions — error-handling style, naming, file layout, what a finished change looks like
  • Scope boundaries — which directories are off-limits, what must never be touched without a human
  • Verification steps — what to run before declaring done, and what "done" means

The file is one of five layers. The rest of the stack is boring and decisive: branch protection with required checks, CI that is fast and flake-free (an agent that can't trust the signal will improvise around it), CODEOWNERS so agent changes route to the humans who own that area, and push protection — which ran 5.8 billion secret scans during the Octoverse year, a number that tells you exactly how often credentials try to walk into git history.

Model Pluralism Got Real

Underneath the PR numbers, the model story quietly went radical. Paid Copilot users worked with 47 distinct models in September, up from 29 in May. Among developers who select their own models, 61% used more than one. Their requests split across the spectrum: 38% to general-purpose models, 37% to deep-reasoning and planning models, 25% to fast and lightweight ones. And 63% of paying developers let auto model selection choose for them at least once in September.

The single-model stack is over. Routing is the workflow now.

This is the death of the "which model do you use?" question. The working answer is "which model for which step" — a fast one for scaffolding, a deep-reasoning one for planning and hard bugs, a generalist for everything in between. For the self-hosting crowd, the same shape is arriving at home: a local model on your own hardware for cheap drafts and boilerplate, a frontier API for the steps that genuinely need it, and a routing layer between them. The skill that matters is no longer loyalty to one model; it's knowing where each one earns its tokens.

Routing is the new skill. Knowing which model to hand each step now beats devotion to any single one of them.

What This Changes for You

If you maintain an open source project

Assume roughly half of your incoming queue is agent-drafted, and decide your policy before the flood rather than after: require an issue link on every PR, require tests for behavior changes, label agent PRs so you can track what the machine contributes, and protect your branches. Your review throughput is now the project's bottleneck — more than funding, more than marketing, more than the issue tracker.

If you're a working developer

The value moved up the stack. Framing the problem precisely, writing the spec, judging the diff — that's where the leverage lives. The person who can describe the work unambiguously now out-ships the person who types fastest. If you haven't written an agent config file for your primary repo, that's an afternoon that compounds every week after.

If you run a team or platform

Credentials are the new leak surface. Agents move at machine speed and they copy-paste with abandon; 5.8 billion push-protection scans in a year is what that looks like in aggregate. Secret scanning and push protection are one-click settings. Turn them on before you scale up agent usage, not after.

The Honest Caveats

  • These are usage numbers, not quality grades. GitHub's methodology notes the figures measure observed platform usage — not model quality, and not a broader industry baseline outside GitHub.
  • The 8x stat is correlation. GitHub itself says so. Agent-ready teams were likely shipping more before the config file existed.
  • Faster merges may describe humans, not agents. Pre-scoped, well-tested work units are easier to approve regardless of who — or what — drafts them.
  • More merged PRs is not more good software. Review debt is real, and a merged PR nobody truly read is tomorrow's incident report.

Where I Come Down

The pull request has quietly stopped being proof of human craft and become a unit of review. The scarce skill in software is no longer producing a diff — it's judging one.

After reading the report, I spent twenty minutes on my own repositories: wrote a proper AGENTS.md, turned on branch protection with required status checks, added a CODEOWNERS file, and started labeling agent PRs so I can actually measure what the machine contributes. Will the 8x multiplier visit my little blog repo? Probably not — the teams in that stat were shipping at a different scale. What I expect instead is fewer garbage agent contributions, faster reviews, and a repo that keeps working as agents get more capable every month. That part is fully under my control.

The agents showed up for the pull request the way cloud computing showed up for infrastructure — gradually, then in the default settings. Forty percent is not the end state; it's the midpoint of a six-month curve that is still pointing up. The only question worth asking in November is whether your repository is ready for the other half.
