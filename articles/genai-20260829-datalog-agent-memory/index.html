Your AI Agent Doesn't Need a Bigger Context Window. It Needs a Database.

August 29, 2026 · 10 min read · Agents, AI Infrastructure, LLMs

"Memory" has been hiding two different problems. Vector databases only solve one of them.

Every developer who has run an AI agent past the two-hour mark knows the failure mode. The agent had it, and then it didn't. It suggests an approach your session ruled out ninety minutes ago. It keeps reasoning from an assumption the debugger already disproved. And when you correct it, the retraction goes exactly one layer deep — everything built on top of the wrong belief survives, quietly poisoning the rest of the investigation.

The industry's default answer is to throw more context at the problem: longer windows, summarized transcripts, RAG over old conversation turns. Then last week, a security researcher named Jordy Zomer posted a writeup that hit the front page of Hacker News (259 points) with a different answer entirely. He wanted his vulnerability-research agent to stop forgetting why it believed things — and in solving that, he accidentally built what is essentially program analysis for LLM memory.

The project is called Lemmalog: a Datalog engine that maintains what an agent currently knows, invalidates dead conclusions automatically, and can answer "why do you believe this?" with a full provenance tree. The benchmark numbers attached to the idea are what turned a nice blog post into a signal.

The failure mode, stated precisely

Zomer's writeup starts with an experience anyone doing long-horizon agent work will recognize. Mid-investigation, you establish a chain of facts: the attacker controls object_a, object_a points to object_b, object_b is a kernel object. Conclusion: the attacker can control a kernel object.

Two hours later, in the debugger, you discover object_a does not actually point to object_b. The observation was wrong. Now a conventional memory system holds something like this:

  • object_a points to object_b — retracted
  • attacker can control object_b — still sitting there, derived from the retracted fact
  • Both retrieved together, and the model left to hope it sorts out which conclusions still stand

Telling an LLM that something is wrong, as Zomer dryly notes, does not necessarily mean it stops believing everything that depended on it. Retrieval-based memory makes this worse in a specific way: the retracted fact and the conclusion drawn from it are both semantically relevant to your query, so both come back, forever.

During a vulnerability research session, I don't just want the model to remember what we said. I want it to maintain what we currently know.

And then the pivot that makes the whole piece worth reading: he recognized this shape. Facts. Rules that derive new facts from existing ones. A fixed point containing everything derivable. The ability to update only affected results when an input changes. This is not a chat problem. This is program analysis — a field with forty years of solutions.

The architecture: a slightly strange compiler

The LLM is the probabilistic front-end. The database is the deterministic back-end. Neither does the other's job.

Lemmalog's core move is a division of labor that maps cleanly onto how compilers work:

  • The LLM handles the fuzzy part. "LLDB shows the freed object is later reused as the destination of the write" becomes freed(object_a) and reused_as(object_a, write_target). Extraction happens once per conversation, chunked and cached — you pay for it once, not per question.
  • The Datalog engine handles the deterministic part. Given facts and rules, it computes and maintains every consequence. When an input fact changes, incremental evaluation updates exactly the affected conclusions — not the whole knowledge base, and not the model's vibes.
  • Another LLM invocation is the back-end, turning maintained state back into natural language, next steps, or actions.

The amusing part is that our parser is probabilistic, while everything after it does not necessarily have to be.

For anyone who has spent time with SQL databases, Datalog is the declarative cousin: you write what is true and what follows from what, not how to compute it. A rule like controls_kernel_object(A) :- controls(A, X), points_to(X, Y), kernel_object(Y) says that attacker-controlled objects pointing at kernel objects make kernel objects attacker-controllable. The engine figures out the rest, including what to un-derive when a premise dies.

The three hard problems, and how a database solves them

1. Retraction with dependencies

Deleting facts sounds trivial until you hit this:

a.
b.
c :- a.
c :- b.

c has two independent justifications. Remove a, and c survives — b still supports it. Remove both, and c dies. An agent's conclusions are exactly like this: an exploit candidate stays viable through multiple independent primitives, and it should only collapse when its last support does. Lemmalog tracks how every derived fact was produced, so removal propagates correctly instead of bluntly.

2. Provenance — "why do you believe this?"

The same dependency tracking gives you explainability almost for free:

candidate_3_is_exploitable
|
+-- attacker_controls_pointer
|     +-- observation_41
+-- pointer_reaches_target
      +-- observation_57
      +-- rule_12

This quietly fixes one of the most annoying LLM failure modes: the model confidently asserts "we already established this pointer is attacker-controlled" when no such thing was established. In Lemmalog, if a conclusion has no provenance, it is not part of the maintained state. It doesn't stop the model from hallucinating during extraction — but it makes it much harder for unsupported claims to silently become load-bearing.

3. Facts that change over time

Replacing a belief isn't the same as deleting it. When primitive_a goes from viable to not-viable, the current state should say "not viable" — but if you later want to know why you explored that strategy for two hours, the old state matters. Lemmalog attaches validity intervals to facts: viable(primitive_a) [10:14, 12:37), not_viable(primitive_a) [12:37, ...). Both "what's true now" and "what did we think then" are queries, not contradictions.

Why not just use a vector database?

This is the section that elevates the piece from a cool project to a thesis. Zomer's point is that "agent memory" has been conflating two different questions:

  • Retrieval: what information from the past is relevant to this question? Vector databases are genuinely good at this.
  • Maintenance: given everything we've learned, what is currently true? Nobody's vector store does this, because cosine similarity has no idea that a stored statement was disproven two hours later, or that five other conclusions depended on it.

Cosine vibe similarity and truth are not quite the same thing.

His current setup combines both: structured state for what's true, hybrid retrieval (BM25, entity-graph boosts, embeddings) for what's relevant, and the original source text kept around for when structure loses nuance. That hybrid shape — not either/or — is probably where this field lands.

The numbers: honest, mixed, and interesting

Lemmalog sits third among dedicated memory systems — but more than doubles full-context accuracy at 1/38th the tokens.

Zomer did the thing more people building memory systems should do: he ran standardized benchmarks, three times each, and published where his system loses. On LongMemEval (102 questions across single-session facts, multi-session, temporal reasoning, and knowledge updates), three runs gave F1 0.463 ± 0.010:

  • PropMem: 0.550 — still the leader
  • SimpleMem: 0.480
  • Lemmalog: 0.463
  • OpenClaw: 0.244
  • Full context (entire history in the prompt): 0.222

So no, Datalog did not win. He says so plainly. But look at the two numbers flanking the comparison. Feeding GPT-4.1 the entire conversation scored 0.222 F1 — and Lemmalog more than doubles that while passing the answering model ~2,700 tokens per question instead of ~104,000. On LoCoMo (10 long conversations, 1,986 questions, much harder to get lucky on), the pattern repeats: Lemmalog 0.533, behind PropMem's 0.605 and OpenClaw's 0.557, ahead of full context's 0.542 — at ~3,400 vs ~18,900 tokens per question. Extraction with Claude Sonnet 4.6 is paid once, cached per conversation.

And the cost curve is the real story for agent builders. Full-context prompting pays for the entire history on every query:

  • Turn 50: ~100K tokens/query vs ~2.5K
  • Turn 100: ~200K tokens/query vs ~2.5K
  • Turn 500: ~1M tokens/query vs ~2.5K — except 1M doesn't fit, and the session dies

Where it wins, where it loses

The category split is the thesis: structure wins exactly where maintaining state matters, and loses where nuance gets flattened.

The category-level results are more interesting than the averages, because they map precisely onto the design:

Where structured memory dominates:

  • Knowledge updates: Lemmalog 0.579 vs PropMem 0.528 and full context 0.202. "We believed A; A is no longer true; what now?" is literally the retraction machinery.
  • Adversarial false premises (LoCoMo): 0.707 vs full context's 0.509. When a question asserts something that never happened, a model with a giant transcript pattern-matches its way to an answer anyway. A structured memory can simply find no supporting fact and say no — which turns out to be a killer feature.
  • Temporal reasoning: 0.257 → 0.454 after one bug fix (more on that below).

Where it genuinely loses:

  • Multi-session recall: 0.211 vs PropMem's 0.582. Diagnosis: the information wasn't mis-connected — it was never extracted. If the extractor never emits a fact about the Airbnb booking, no amount of derivation conjures it.
  • Inferential questions: 0.164 vs 0.289. Flattening "I prefer quiet restaurants, except when traveling with friends" into prefers(user, quiet_restaurants) destroys half the meaning before Datalog ever runs. His proposed fix — conditional rules that stay conditional — is the right instinct.
  • Plain factual recall still trails full context (0.399 vs 0.517 on LoCoMo), which should humble anyone who thinks structured memory is a wholesale replacement.

The debugging stories are the actual gold

The most valuable part of the writeup isn't the leaderboard — it's the failure autopsy. The first standardized LongMemEval configuration scored 0.226. The final one scores 0.463. More than double, and almost none of that came from touching the model. It came from finding six concrete computer-science bugs:

  • The accidental censorship bug. An anti-hallucination instruction — "make sure the answer is actually supported by the retrieved facts" — was interpreted as refuse unless one fact literally contains the answer. Score dropped to 0.371; 32 of 102 questions were refused, all answerable. "Which airline did I fly most?" has no stored fact answering it — the answer requires counting over flight facts. The fix: refuse when the premise is absent or misattributed, but actually reason when evidence needs combining.
  • The stemmer bug. A relevance filter's plural stemmer only folded words longer than four characters. So owns never matched own, every count line got silently dropped, and counting questions received no counts. Classic.
  • The date bug. Date-like values were compared as interned Datalog symbols, and the engine's < operator compares internal symbol IDs — not dates. Normalizing to integers and deriving happened_before from real timestamps bought nearly twenty F1 points in temporal reasoning.
  • Entity resolution. "I bought a Honda Civic" / "my car broke down" / "the Civic is fixed" became three unrelated objects: honda_civic, car, civic. A reconciliation pass connecting mentions to canonical entities was worth real points.

None of those required making the language model larger. They required maintaining better state around it.

That sentence is the whole article, as far as I'm concerned. We keep reaching for bigger models and longer windows to fix what are, at bottom, data-engineering problems wearing an AI costume.

What this means for agent builders

I build long-running agents — my own production setup runs multi-hour research and ops workflows on a headless home server, and I've hit every failure mode in Zomer's intro. Here's what I'd actually take from this piece:

  • Stop treating the transcript as the source of truth. The transcript is a log. Logs are for audits; state is for decisions. If your agent's beliefs live only in message history, invalidation is impossible by construction.
  • Long-horizon sessions need provenance, not just memory. "Why do you believe that?" should be a query with a real answer — observation IDs, rules, and timestamps — not a request for the model to reconstruct its feelings.
  • Flat query cost is an architecture property, not an optimization. ~2.5K tokens per query at turn 50 and at turn 500 changes what agents you can afford to run at all. Full-context agents have a hard ceiling where the session stops fitting.
  • The front-end dominates. The Datalog engine didn't get smarter between 0.483 and 0.533 on LoCoMo — the extraction, entity resolution, and retrieval did. If you build one of these, most of your iterations will be parser engineering, not logic engineering.
  • Structured memory can say "no." The adversarial score (0.707 vs 0.509) is the sleeper result. Agents that verify premises against maintained state instead of pattern-matching transcripts are categorically harder to fool — and given everything 2026 has taught us about prompt injection and agent blast radius, that's not a benchmark nicety. It's a security control.

Verdict

Lemmalog is not the best memory system on the leaderboard, and Zomer is admirably upfront about it — PropMem still beats it on both benchmarks, LoCoMo is a conversational-memory test rather than a vulnerability investigation, and 102 questions is a small sample. His own next experiment is the honest one: point a long-horizon agent at a real investigation and see if maintained state stops it from resurrecting dead hypotheses.

But as a directional signal, this lands. The idea that an agent's knowledge should live in a database with rules, retractions, and provenance — with the LLM as a probabilistic parser at the edges — is old AI (logic programming never died, it was waiting) executed with new-world benchmarks. The source is open on GitHub, and it ships with an MCP server, which means your existing agent can use it today without changing frameworks.

We keep asking for bigger context windows every time an agent forgets something. Sometimes the answer is that the agent should have been maintaining state all along — and we've known how to build that part for decades.
