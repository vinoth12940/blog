Pi Durable: Crash-Safe Agents Are Finally a Library, Not a Platform

Every self-hoster who runs agents has met 3:07 a.m. That's when the container restarts, the laptop sleeps, or the unattended-upgrades timer reboots the box — and the agent that was forty minutes into a delicate multi-step task wakes up as nothing. No transcript, no plan, no memory of which steps completed. You re-read logs, re-pay the tokens, and hope nothing half-finished fires twice.

On October 1, the Pi project hit its long-promised 1.0 — and shipped an answer to exactly this problem. It's called Pi Durable, it hit the Hacker News front page twice in one day (Pi 1.0 at 1,675 points, Pi Durable at 499), and it does something the agent ecosystem has been improvising around for two years: it makes the agent's execution itself durable, not just its chat log. The repo — 112,000 stars, MIT licensed, TypeScript — is now a toolkit for both the terminal coding agent you drive and the long-running agents that drive themselves.

I've written before about agent containment — fences, kill switches, what happens when agents get their own computers. This is the other half of that story: the boring, load-bearing infrastructure that decides whether an agent that survives a crash is a recovering professional or an amnesiac with root access. Pi Durable is the most interesting take on it I've read this year, and I think it marks a phase change in how we build long-running agents.

The promise in one picture: the crash is an event in the run's history, not the end of the run.

What actually shipped on October 1

First, the backstory, because it explains the design. Pi is a minimal coding agent created by Mario Zechner, known for taking a hard line against feature creep — Zechner famously dismissed MCP as unnecessary, right up until Pi 1.0 shipped native MCP support, a reversal The Register covered under the headline "Pi coding agent pulls a 180." In April 2026, Pi was acquired by Earendil, a company formed by Armin Ronacher — the creator of Flask — and Colin Daymond Hanna. That pedigree matters: Pi has been described as "the Flask of agent harnesses" and, less charitably but just as accurately, "the Neovim of harnesses." Minimal, hackable, fiercely opinionated about what stays out.

Pi 1.0 itself is a hardening release. The feature list is short by design:

  • Codemode — a harness-side sandbox where the agent writes and runs scripts instead of issuing one tool call at a time, with native support for MCP servers, decision models like Jev, and image models.
  • Virtual models — extension-defined routers, so a "model" can plan with Claude Opus and implement with GPT, handing off mid-conversation.
  • Deferred tool loading and cache warming for Anthropic models — token economics as first-class features.
  • Mid-conversation system messages — prompt and tool changes that land mid-run without nuking the prompt cache.

The more consequential release is the one that doesn't replace the coding agent at all. Pi Durable is an experimental npm package — @earendil-works/pi-durable, first published September 19 — that extracts everything Pi knows about running agents into a library for building your own long-running agentic applications. Same MIT license, same minimalism, different ambition: the terminal agent runs one conversation for one person; Pi Durable runs many conversations for many clients, indefinitely, and survives everything up to and including its own process dying.

One shared core, two products: the harness you drive, and the substrate that runs without you.

The mechanics: how an agent survives its own death

Pi Durable's core abstraction is almost aggressively boring: everything is a task, and every task checkpoints before it runs. A model call is a task. A tool call is a task. Compaction is a task. Each one stores its intent in storage — your choice of in-memory, SQLite, or JSONL — before it executes. When the process dies and a new process opens the same storage, it finds the unfinished tasks and continues each from its last checkpoint.

The details are where the design earns its keep:

  • A model call cut off at 80% is resent on resume — and the partial answer stays in the transcript, explicitly marked as aborted. No silent corruption of context.
  • A tool call reruns only if it declared itself safe to rerun. Tools carry a replay policy; a search can freely re-execute, but an interrupted side-effecting call is instead reported to the model as interrupted, with whatever output was stored — and the model decides what to do next. The harness doesn't pretend to know whether your deploy went through.
  • Queued messages are still queued after a crash. A requestId makes a submission exactly-once: a client that retries after a crash gets the original submission's answer back instead of creating a second job.
  • Subagents are just conversations — each one durable in its own right, so a rerun tool finds its subagent where it left off and waits for the answer it already owes you.

Even the approval flow is crash-aware. Hooks — extension code that can intercept and block tool calls — store their decisions in a memo where the first write wins. If your human-in-the-loop deploy approval happened before the crash, a restarted hook reads the memo instead of asking the human again. Anyone who has been re-paged at 4 a.m. for an approval they already gave will feel that one.

That third row deserves a special word, because I've run into it personally. My article-publishing pipeline runs on a queue that pops the item before the work executes — the item is marked in-flight, and if the process dies mid-publish, the item is simply gone. No error, no retry, a silent loss that took real forensics to diagnose. That is the exact bug class requestId-keyed submissions exist to eliminate: the pop and the work become one recoverable unit instead of a gap you discover weeks later. If your agent queue can lose a job to a crash without anyone noticing, you don't have a queue — you have a suggestion box.

This is Temporal's playbook, sized for one engineer

If you've worked with workflow engines — Temporal, AWS Step Functions, Celery with a stiff upper lip — none of these primitives are new. Checkpoint-before-execute, replay policies, idempotency keys, exactly-once semantics: that's the durable-execution canon, a decade old. What's new is the packaging and the frame.

Four primitives, one idea: intent is recorded before effects, so recovery is mechanical.

Workflow engines treat the model as one activity among many inside a deterministic program you write. Pi Durable inverts that: the conversation is the program. The model's transcript, the tools it called, the state it committed — all of it is the durable workload, checkpointed as it goes. Storage is pluggable and boring on purpose: the SQLite and JSONL backends use no Node-specific APIs, so the same harness runs on Node, Bun, or inside a Cloudflare Durable Object, and the storage interface is small enough to implement over Postgres or a key-value store in an afternoon. On SQLite, the harness keeps only the working set in memory — active transcripts are naturally bounded by the context window, because compaction summarizes older messages before they overflow it. A conversation with tens of thousands of messages fits comfortably in RAM.

And the whole thing is about 15,000 lines of TypeScript — the Earendil post computes it as roughly 150,000 tokens for GPT-class models, 250,000 for Claude. That number is the pitch. This is infrastructure you can actually read: point your coding agent at the source, have it study the thirty-plus examples, and understand your own runtime. Try that with an orchestration platform's control plane.

Where this sits among the storage philosophies

Agent state persistence has four dominant schools right now, and it's worth placing Pi Durable among them honestly:

Data surviving a crash is not the same as execution surviving it. The gap between those two is where long-running agents go to die.

  • In-memory loops — the default nobody chose. The transcript is a list in RAM. Fine for one human's terminal session; helpless against deploys, OOM kills, and lid-close.
  • JSONL transcript files — the pragmatic middle. Your data survives, and you can grep it, but recovery is a human procedure and there's no notion of concurrent, forkable execution.
  • Workflow engines — bulletproof and operationally heavy. A cluster, SDK ceremony, determinism constraints, and a mental model where the LLM is a step, not the star.
  • Library-grade durable harnesses — Pi Durable's bet: strong durability, no platform tax, sized for a single engineer to hold in their head.

The ecosystem context makes this bet interesting. The HN thread on Pi Durable turned into an instant survey of the space: LangChain's Deep Agents, Vercel's Eve, OpenAI's Agents API, Anthropic's managed agents — every major player is shipping in this exact category, but almost all of them as SDKs or hosted products. Pi Durable is close to alone as a library — no account, no control plane, storage you own. One commenter nailed the open question: do durable agent setups want a complete-product approach, or do people want to compose them as libraries? The next two years answer that. But the fact that the question is being asked at all tells you the category has crossed from hack to infrastructure.

What I'm changing in my own deployments

I run agents on a home server — cron-scheduled writers, watchers, a publishing pipeline — and the durability gap is not hypothetical there. The classic failure: the nightly agent is mid-task when the monthly security update reboots the box. Transcript in a dead tmux buffer, downstream jobs none the wiser.

Self-hosted agents have always been one unattended-upgrades away from amnesia.

Regardless of whether you adopt Pi Durable specifically, its release is a good forcing function to audit your own stack. The checklist I'm applying, each item mapped to a mechanism rather than a vibe:

  • Can my agent's run survive its own process dying — automatically? Not "can I reconstruct it from logs." Can a systemd unit restart, reopen state, and continue without me. If the answer needs a human in the loop, the answer is no.
  • Do I pop queue items before or after the work? Pop-after-complete, or key items with an idempotency token so a replay can't double-fire. Audit this before you trust any agent with anything billable.
  • Does every side-effecting tool declare whether it's safe to rerun? Reads are free to replay. State-changing calls need either idempotency keys or an explicit "I was interrupted, here's what got out" path. Undeclared is a bug, not a gray area.
  • Are human approvals memoized? An approval given should survive a restart. Re-asking the human for the same decision is a durability bug wearing an etiquette hat.
  • Is state where I can see it? SQLite files I can back up, inspect, and diff beat a SaaS dashboard I can't export. The library approach makes the boring storage choice a feature.

The caveats, honestly

Pi Durable is labeled experimental by its own authors, and the API may still change — they say so plainly in the announcement. It's TypeScript-first; the FAQ waves at a possible Rust port but ships nothing of the sort today. The application-state documents are restricted to JSON, which at least one HN commenter found limiting for outbox-style sync with external stores. And Earendil is a VC-backed startup, which fuels the unavoidable speculation about acquisition and independence — a fair concern for anyone building on a company's substrate rather than a foundation's standard. None of these are disqualifying. All of them belong in your evaluation. The mitigation for most of them is the same: the code is small enough to fork, and the storage format is yours from day one.

The takeaway

The agent ecosystem spent 2025 and early 2026 arguing about capability — which model, which benchmark, which harness tops which terminal test. The next argument is already visible, and it's quieter: what happens when the agent keeps running after you stop watching. Pi 1.0 says the coding-agent harness has matured into stable infrastructure. Pi Durable says the layer above it — durable, inspectable, library-grade execution — is where the interesting engineering now lives.

The teams building always-on agents learned what backend engineers learned twenty years ago: stateless hope is not an architecture. Crash-safety used to require a platform team and a control plane. As of October 1, it requires an npm install and an afternoon of reading source.

An agent whose memory dies with its process isn't autonomous — it's a goldfish with shell access. Durability is what separates the two.
