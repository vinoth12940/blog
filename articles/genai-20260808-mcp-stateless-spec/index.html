MCP Just Went Stateless: The Protocol's Biggest Rewrite Yet

On July 28, 2026, the Model Context Protocol shipped its most consequential update since launch: a complete transition from a stateful, bidirectional protocol to a stateless, request/response model. The Core Change: Goodbye Sessions, Hello Stateless

The headline feature of the 2026-07-28 specification is the elimination of the stateful session model. Here's what that means concretely.

The Old World (Spec 2025-11-25)

In the previous spec, every client-server interaction began with a formal handshake:

  1. Client sends initialize with its capabilities
  2. Server responds with serverInfo, protocolVersion, and a Mcp-Session-Id
  3. Client confirms with notifications/initialized
  4. All subsequent requests must carry the session ID

This worked for development, but it created real problems in production:

  • Single-instance bottleneck: If a server held session state, you couldn't route requests to other instances
  • Held-open connections: Server-to-client requests (elicitation, sampling) needed a persistent bidirectional stream
  • No failover: If the server instance died, the session died with it — no recovery path
  • Load balancer hostility: Sticky sessions became mandatory, defeating the point of horizontal scaling
The problem: Every session-bound server is effectively single-instance. You can't put it behind a round-robin load balancer without sticky sessions, and you can't failover without shared session storage. For a protocol that's supposed to be the standard interface for AI agent tool-use, that's a scalability ceiling.

The New World (Spec 2026-07-28)

The new spec eliminates the handshake entirely. Every request is now self-describing:

  • Each request carries its protocol version, client identity, and capabilities in _meta
  • No initialize / initialized exchange required
  • No Mcp-Session-Id header
  • Any request can land on any server instance behind a plain round-robin load balancer

There's an optional server/discover RPC for clients that want to learn server capabilities up front — but it's not required. A client can fire off a tools/call on its very first request, and the server will handle it.

The old flow required 4+ round trips with a held-open connection. The new flow is a single fire-and-forget request.

Here's what a stateless request looks like on the wire:

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" }
  },
  "_meta": {
    "io.modelcontextprotocol/clientInfo": {
      "name": "my-app",
      "version": "1.0"
    }
  }
}

That's it. No handshake, no session, no held-open stream. The response comes back and the connection is done.

💡 What about application state?

Going stateless at the protocol level doesn't mean your app can't be stateful. If your server needs to carry state across calls, the spec recommends minting an explicit handle from a tool and having the model pass it back as an argument. The key insight: the model can see the handle and thread it between tools, which works better than session state hidden in the transport.

Six More Changes That Matter

The stateless core is the headline, but six additional features make this spec release significant:

The full feature set of the 2026-07-28 specification — from MRTR to authorization hardening.

1. Multi Round-Trip Requests (MRTR)

Sometimes a tool needs input from the user mid-call — a confirmation, a missing parameter, a choice between options. The old spec handled this through server-initiated requests that required a held-open stream. MRTR replaces that with a stateless pattern:

  • Server returns resultType: "input_required" along with the questions
  • Client retries the original call with answers attached in inputResponses
  • No persistent connection needed

This is a clean solution that works within the stateless model. The server doesn't need to hold a connection open while waiting for a response — it just returns what it needs and lets the client come back.

2. Header-Based Routing

Streamable HTTP requests now must include Mcp-Method and Mcp-Name headers. This is a small change with big infrastructure implications:

  • Your API gateway can route requests by method without parsing JSON bodies
  • Rate limiters can meter tools/call vs tools/list differently
  • WAFs can apply policies at the header level
  • Observability tools get method-level metrics "for free"

If you've ever tried to route JSON-RPC traffic through an API gateway, you know how painful body-parsing for routing is. Headers solve this cleanly.

3. Cacheable List Results

Responses from tools/list, prompts/list, resources/list, and resources/read now carry ttlMs and cacheScope fields. This enables:

  • Client-side caching of tool catalogs — reducing redundant fetches
  • Deterministic ordering — keeping upstream LLM prompt caches stable across reconnects
  • Lower latency for repeated agent sessions

4. Authorization Hardening

The spec team noted that authorization is where implementers spend most of their integration time. This release brings several security improvements:

  • RFC 9207 issuer validation: Clients must validate the iss parameter before redeeming authorization codes — closing an authorization-server mix-up vulnerability
  • Credential-issuer binding: Client credentials are bound to the issuer that minted them — no reuse across authorization servers
  • DCR deprecation: Dynamic Client Registration is formally deprecated in favor of Client ID Metadata Documents (CIMD). The CLI localhost redirect issues that plagued desktop apps? application_type during DCR fixes that as a hardening measure

5. Tasks as a Formal Extension

Tasks moved out of experimental status and into the io.modelcontextprotocol/tasks extension. The new task lifecycle uses poll-based tasks/get and tasks/update, with change notifications moving to a single subscriptions/listen stream. This is the foundation for long-running, asynchronous agent workflows.

6. Formal Deprecation Policy

The spec now includes a twelve-month minimum deprecation window. Roots, Sampling, and Logging are deprecated but still functional. The legacy HTTP+SSE transport gets a year-long offramp. This means you can plan upgrades instead of reacting to breaking changes — a crucial maturity signal for production teams.

Migration: What You Need to Do

Breaking changes, deprecations, and what stays compatible. The good news: backward compatibility is built in.

If You're Building a Server

  • Remove initialize / initialized handling — replace with server/discover RPC
  • Drop session state dependencies — move to tool-argument-based handles for stateful workflows
  • Add Mcp-Method and Mcp-Name to your HTTP headers
  • Implement resultType: "input_required" for tools that need mid-call user input
  • Add ttlMs and cacheScope to list responses

If You're Building a Client

  • Stop sending initialize — go straight to tools/call or use server/discover for capabilities
  • Handle MRTR responses (input_required) by prompting the user and retrying
  • Cache list responses based on ttlMs
  • Validate iss parameter per RFC 9207 in OAuth flows

Backward Compatibility

The team built in real backward compatibility. A v2 server answers the legacy initialize handshake alongside the new server/discover method. This means upgrading your server doesn't strand existing clients — clients on the 2025-11-25 spec keep connecting. The client's default mode probes server/discover first and falls back to initialize on older servers.

Key takeaway: The migration path is incremental, not cliff-edge. You can upgrade your server today and existing clients keep working. You can upgrade your client today and it falls back gracefully on old servers.

Why This Matters for the Agent Ecosystem

The shift to stateless is more than a technical optimization. It's a signal that MCP is growing up as production infrastructure.

Stateful protocols are fine for development tools and single-user scenarios. But when 28% of Fortune 500 companies are deploying MCP servers in production, when 97 million SDK downloads happen every month, and when every major AI platform depends on the protocol — stateful doesn't scale. You need:

  • Horizontal scalability behind any load balancer
  • Stateless failover so a crashed instance doesn't kill active sessions
  • Gateway-friendly routing for enterprise security and observability
  • Predictable caching to reduce latency at scale

The 2026-07-28 spec delivers all four. The breaking changes are real, but the migration path is well-paved with backward compatibility and a twelve-month deprecation window.

My Take

I run an AI agent on a home server that uses MCP-like tool-calling patterns extensively. The shift to stateless resonates because I've hit the exact scaling wall this solves — sessions that die when a process restarts, load balancers that can't route intelligently, and the overhead of maintaining connection state for what should be simple RPC calls.

The MCP team made the hard choice here. They could have layered stateless-friendly features on top of the stateful core, creating a confusing dual-model. Instead, they ripped out the session model and rebuilt around request/response. That's the kind of decision that pays off over years, not weeks.

The extensions framework — with Tasks, MCP Apps, and Enterprise Managed Authorization — tells me this protocol is thinking beyond "connect an AI to a database" and toward orchestrating complex, multi-step, enterprise-grade agent workflows. The formal deprecation policy tells me they're serious about production stability.

If you're building AI agents and haven't looked at MCP yet, the 2026-07-28 spec is the version to start with. It's the first one that feels like it was designed for the scale the ecosystem has actually reached.
