Microsoft's Agent Framework Was Hijacked on PyPI — Rotation Won't Save You

November 21, 2026 · AI / Security / DevOps · 9 min read

On November 17, someone published two versions of agent-framework — Microsoft's official open-source toolkit for building AI agents — to PyPI. They came from Microsoft's own publisher account. They looked like a routine update to a package with roughly 192,000 monthly downloads. And both of them carried a credential stealer that runs every time Python starts, whether or not you ever import the framework.

By the time PyPI quarantined both releases, roughly an hour had passed, the attacker had demonstrated they still held valid publishing access, and the malware had moved on to something uglier than stealing keys: asking cloud providers to mint fresh tokens from the compromised machine's own managed identity and CI federation.

I've spent the last two days reading the incident reports from Wiz, Socket, StepSecurity, and OX Security, and I think this is the most instructive supply-chain attack of the year — not because of who got hit, but because of what it teaches about the assumptions we build our Python workflows on. Every one of them — "my dependency file tells me what runs," "rotation cleans up a leak," "my build runner is plumbing, not a credential" — died this week.

Why this package, specifically

Agent Framework is Microsoft's consolidation of its Semantic Kernel and AutoGen lines — the toolkit it now positions as the official way to build AI agents and multi-agent workflows in Python. It sits at the center of exactly the kind of development the whole industry is pushing right now: agents that hold API keys, call tools, touch cloud resources, and run inside CI pipelines.

Which is precisely what made it a target. An agent framework is, by design, connective tissue — its whole job is to hold credentials and use them. Compromise one install on one developer machine or one build runner, and you inherit everything that environment can reach: cloud consoles, package registries, git providers, container registries, model hubs.

An agent framework is the software category whose literal purpose is holding API keys and authority. Of course the supply-chain attackers came for it.
  • Package: agent-framework — Microsoft's official PyPI project, ~192,534 monthly downloads per OX Security
  • Poisoned versions: 1.26.1 and 1.26.2, both published November 17, 2026
  • Last clean version: 1.26.0 — everything above it on the index that day was hostile
  • Caught by: Socket, StepSecurity, and OX Security, independently

The 70-minute window

The timeline shows both sides moving fast. PyPI quarantined the first malicious release quickly — real credit to the automated detection that Socket, StepSecurity, and OX Security's telemetry feeds enable. Then the attacker did something that should reframe how you think about this incident: they published 1.26.2 about two and a half minutes later. PyPI caught that one too, roughly eight minutes after upload. But the message was unmistakable — quarantining packages does not revoke whatever publishing credential the attacker was using.

And what a credential it was. Wiz's analysis traced the publishing access to a client certificate and private key for Microsoft's Engineering System Release Pipeline — the internal service Microsoft uses to sign and publish its own packages. The service's address filtering actually blocked the attacker's first attempt, which came from AWS address space. The second attempt came from Microsoft-owned address space and went through. How the certificate leaked is still unknown; Microsoft had not responded to press inquiries as of the latest reports.

The certificate got them in; the 2.5-minute re-publish proved they still held it.

One more detail from Wiz's report that I can't stop thinking about: the attacker's own operational tooling reported its progress to the same public webhook it was using to collect stolen data, and identified itself as Cairn — an open-source, AI-powered penetration-testing framework. The AI-security story of 2026 has mostly been about AI defending or AI attacking vulnerabilities. This was quieter: AI tooling managing the logistics of a supply-chain heist, timestamping its own work into a webhook any defender was also reading.

The trick that beats your dependency audit

Here's the part every Python developer should internalize. The payload wasn't delivered through the package's importable code. It was delivered through a .pth file — a file type Python executes automatically at interpreter startup, processing it before your application code, before your imports, before anything.

Version 1.26.1 planted the hook as agent_framework_meta.pth, pointing at a module innocuously named _telemetry.py. When researchers caught it, version 1.26.2 restored Microsoft's original package initializer and moved the payload to af_runtime_diag.pth — a fresh name, a smaller diff, harder to spot. Both versions kept the genuine agent-framework-core 1.26.0 as their dependency, so the framework functioned perfectly normally while the stealer ran underneath.

The best camouflage for malware is a product that works exactly as advertised. Your import scanner had nothing to find, because the malicious code never appears in an import statement.

This is the assumption that died: my dependency file tells me what code runs in my environment. It doesn't. A .pth hook lives one level below the import system. Cloudsmith's head of security James Matchett put the operational consequence bluntly: a production dependency list might show no trace of the framework at all, while a build runner installed it and was shut down before anyone's alert fired.

What it copied — and what it minted

Once running, the malware did two things, and the second is the one that matters for the rest of this decade. First, the expected part: it swept environment variables whose names matched TOKEN, SECRET, AZURE, AWS, or GITHUB; read the environments of up to 300 other running processes; copied .env files; and lifted credential files for Azure CLI, pip, npm, git, Docker, and Hugging Face.

Then the part that changes incident response. Per Endor Labs, it requested Azure managed-identity tokens for 12 separate resources. It requested Azure DevOps OIDC federation tokens. Version 1.26.2 added GitHub Actions OIDC tokens and started scanning GitHub runner directories. This wasn't a burglar copying what was in the drawer — it was asking the bank to issue new cards, in the victim's own name, from the victim's own address.

Copied secrets rotate. Minted tokens don't — they need their own revocation path.

To be fair to the ambiguity: StepSecurity explicitly cautioned that these token requests were attempts, with no confirmation any tokens were actually issued. And per malware trackers at OpenSourceMalware, this was a focused credential and token stealer — no persistence, no RAT behavior. It stole, sent, and left. The haul was compressed, encoded, and exfiltrated in a single request to an attacker-controlled webhook.site endpoint.

A build system that can ask a cloud provider for new access tokens is itself a credential. — Eric Paulsen, Field CTO EMEA, Coder

Three victims — and why that number misleads

The blast radius estimate comes with an asterisk the size of the number itself. Wiz observed the attacker's free webhook.site account, which retained just 50 requests. Of those, 17 represented data thefts — and only 3 were unique victims. The rest were the attacker's own machines and the automated traffic of sandbox and security-vendor scanners.

So: three confirmed victims. That's the good news, and I'd treat it as preliminary for three reasons. The free webhook retained only the most recent 50 requests — anything earlier is invisible. Quarantine windows being what they are, installs during that first hour may never have phoned home at all, leaving no trace in anyone's telemetry. And a compromised build runner that touched a deployment token before being torn down leaves exactly no evidence in the places teams usually look. "Three victims" is the floor, not the census.

This is now a pattern, not an incident

Zoom out and this stops looking like a one-off. In May, Microsoft's durabletask PyPI package was hijacked after its publishing token was stolen — an attack attributed to TeamPCP, the same group behind the LiteLLM compromise. OVHcloud's CLI releases got backdoored on GitHub for developer secrets. Wiz has not linked this month's certificate theft to TeamPCP, but the target selection is converging: the packages developers trust to talk to AI infrastructure are the ones being poisoned. The LiteLLM releases pipeline, the durabletask token, and now a Microsoft signing certificate — each breach walked one step further up the trust chain.

That last hop is the disturbing one. Previous PyPI hijacks stole a maintainer's token. This one used a certificate for the pipeline that signs and publishes — closer to the source of trust itself. If you're a platform engineer, the question this incident should plant is uncomfortable: how many steps are there between a leaked credential and your production dependency tree, and do you actually know where they all are?

Rotation is the beginning now, not the finish line

The standard breach response — rotate your secrets — is exactly half right here, and the half that's wrong is the dangerous half. Rotating stored keys does nothing to tokens already minted through managed identity or OIDC federation. Those live in the identity provider's ledger, not in your .env file. StepSecurity's guidance is that teams need to review OIDC permissions, federated credentials, and managed-identity role assignments as their own distinct workstream.

If you installed either 1.26.1 or 1.26.2, the vendor consensus sequence is:

  • Isolate the machine or runner first — before running python or pip again, because every interpreter start re-fires the hook
  • Rebuild from a known-clean base, pinning agent-framework to 1.26.0, the last clean release
  • Treat every secret reachable from that host as compromised — OX Security's phrasing, and the right one
  • Rotate stored secrets AND review federated access — OIDC configs, managed-identity role assignments, CI federation trusts
  • Check egress logs for the webhook path, distinguishing blocked requests from completed transfers — that distinction is the difference between "exposed" and "breached"

The defense playbook

The longer-term fix isn't a package manager setting — it's shrinking what any single install can reach. Within 48 hours, five security vendors' guidance had converged on the same six layers, and each one maps cleanly onto a step of this specific attack:

Six layers from five vendors' guidance, each mapped to the step of the attack it defeats.

  • Resolve from an internal mirror of approved versions. The public index is a distribution channel, not a trust boundary. Internal mirrors turn "whatever published last night" into "what we reviewed."
  • Treat your build system as a credential. Paulsen's framing is the right mental model — if a runner can mint tokens, the runner IS a key. Audit OIDC federation and managed-identity assignments with the same rigor as secrets.
  • Run builds ephemeral. Environments deleted after each job cap the blast radius of anything that fires during a build — and there's nothing persistent for a stealer to come back to.
  • Expire credentials within the hour. A leaked token with a 60-minute TTL is worth a fraction of a leaked long-lived key. Most CI platforms support this today; the friction is organizational, not technical.
  • Allow-list egress from dev machines and runners. The entire exit of this attack was one HTTPS POST to a public webhook service. Egress filtering doesn't prevent the theft — it prevents the delivery, which is nearly as good.
  • Monitor startup hooks, not just imports. .pth files in site-packages are a legitimate mechanism that this attack weaponized. A diff of unexpected .pth files is cheap to collect and would have flagged both malicious releases instantly.

Stepping back: the genuinely new thing here isn't the stealer — info-stealers in npm and PyPI packages are regrettably routine. It's the combination. A signing-pipeline certificate got them in past the obvious controls. A startup hook got them execution without a trace in any import graph. And identity federation turned a stolen session into the ability to mint unlimited fresh authority. Three force multipliers, one package, 70 minutes.

And the target choice tells you where this is heading. The tools we're all adopting to build agents are, structurally, credential orchestration layers — that's what makes them useful, and it's what makes their supply chain the highest-leverage attack surface in the Python ecosystem. The next inflection of AI security isn't a model misbehaving. It's the plumbing underneath every agent quietly becoming the thing worth stealing.

Trust on install is the vulnerability. Everything else — the certificate, the hook, the tokens — is just exploitation of it.
