The Two-Minute Context

If you've used Claude Code, Cursor, Cline, or basically any agentic AI tool in 2026, you've used MCP — even if you didn't know it. The Model Context Protocol is the open standard that lets an AI model securely reach into external systems: your filesystem, a Postgres database, the GitHub API, a Slack workspace, an internal microservice. Instead of every AI app building custom integrations for every tool, MCP provides one universal plug-and-play protocol.

Anthropic open-sourced MCP in November 2024. By 2025, they donated it to the Agentic AI Foundation (AAIF), a Linux Foundation fund co-founded by Anthropic, Block, and OpenAI. The numbers since then are staggering:

  • 97 million monthly SDK downloads across Python, TypeScript, Go, and C#
  • 10,000+ MCP servers deployed worldwide
  • 78% of enterprise AI teams have MCP-backed agents in production

But the protocol was designed in 2024, when the primary use case was a developer running an MCP server on their laptop for Claude Desktop to talk to. That local-first, single-user origin story baked in a fundamental assumption: sessions. And sessions are now the thing breaking at enterprise scale.

On July 28, the MCP maintainers finalize the 2026-07-28 revision — what Anthropic technical staff member David Soria Parra called "the most substantial changes we have made to the specification, probably since adding authorization." Or, more bluntly: "A lot of things that made MCP are gone."

The core thesis: MCP was built for local single-user demos. The AI community embraced it for enterprise multi-tenant production. The protocol had to grow up — and that meant going stateless.
The fundamental shift: stateful sessions (left) required sticky load balancing and shared state. Stateless (right) lets any server handle any request — scaling like a normal web service.

The Headline Change: Goodbye Sessions

Here's the problem the maintainers had to solve. In the original MCP, every interaction started with an initialize() handshake. The client said hello, the server responded with its capabilities and handed back a session ID. Every subsequent request carried that session ID so the server knew "this is the same conversation."

That works fine when there's one server and one client on the same machine. It falls apart at enterprise scale.

Picture a real deployment. You're running a server for millions of users, behind a load balancer whose entire job is to route each request to whatever server in the farm is free, sometimes in a different region. Now every one of those machines has to know about a session ID that some other machine handed out. It's not impossible, but it's a serious pain, and it fights the load balancer instead of working with it.
— Nate Barbettini, founding engineer at Arcade

The solution is elegantly simple. Under the new revision:

  • The initialize() handshake is removed
  • Protocol-level session IDs are eliminated
  • The protocol version, client identity, and capabilities travel in the _meta parameter on every request
  • A new server/discover method lets clients fetch server capabilities on-demand

As Parra put it: "It's a very smart and nice way to just move state away from the server onto the wire protocol and hope that bandwidth is free." Bandwidth is, effectively, free. Session affinity behind a load balancer is not.

The new MCP now operates exactly like the Claude Messages API — also stateless, also self-contained per request. This is not a coincidence. It's the model the maintainers always wanted.

If your application genuinely needs to carry state across calls — say, a shopping basket or a multi-step workflow — you return an explicit handle (like a basket ID) from a tool, and the client passes it back as an ordinary argument on later calls. The state lives in your application, not in the protocol.

The Six Pillars of the Revision

The stateless core is the headline, but it's one of six major changes. Here's the full picture.

The six pillars of the 2026-07-28 revision. Three are additive (green/blue/purple), two are hardening (amber), one is subtractive (red).

1Stateless Core

The big one, covered above. No initialize(), no session IDs, capabilities ride in _meta. Any request routes to any server instance. Plain round-robin load balancing works out of the box.

2Routable HTTP Headers

In the old protocol, the actual operation (like tools/call) was buried inside the JSON-RPC body. A load balancer couldn't route traffic without parsing JSON. The new revision mirrors routing information into HTTP headers:

  • Mcp-Method header is required on every request
  • Mcp-Name header is required for tools/call, resources/read, and prompts/get
  • Servers reject requests where the headers and body disagree

This is the same pattern that makes REST and gRPC operable at scale. MCP finally joins them.

3Multi-Round-Trip Requests (MRTR)

A stateless protocol still needs a way for a server to ask the client for input mid-call — like a confirmation prompt before deleting a file. The old way: hold a Server-Sent Events stream open. The new way: Multi-Round-Trip Requests.

When a server needs input, it returns an InputRequiredResult object containing the questions and an opaque requestState blob. The client gathers answers, then reissues the original call with the responses and the echoed state. Because everything the server needs is in the payload, any server instance can pick up the retry — no pinning required.

4Authorization Hardening

MCP's authorization model was loose. The new revision tightens it to align with OAuth 2.0 and OpenID Connect:

  • Clients must validate the iss parameter per RFC 9207 — mitigating mix-up attacks (critical when one client talks to many servers)
  • Clients declare application_type during Dynamic Client Registration — so CLI/desktop clients are no longer mis-typed as "web" and rejected for localhost redirect URIs
  • Credentials are bound to the issuing authorization server; scope accumulation during step-up auth is clarified

This is the security story that enterprises need before letting agents touch production systems.

5Deprecated Features

Three core features are formally marked deprecated — on a removal clock, not gone today:

  • Roots — let clients advertise filesystem boundaries to servers. Niche; replace with tool parameters or resource URIs.
  • Sampling — let a server ask the client's model for a completion. Semantics were confusing, rarely used. Replace with direct LLM API integration.
  • Logging — protocol-level notifications from server to client. Too chatty. Replace with OpenTelemetry, stderr, or stdio.

Deprecated features remain functional for at least 12 months, but they're on the clock. Also: the error code for a missing resource changes from the MCP-custom -32002 to the JSON-RPC standard -32602 (Invalid Params). If you match on the literal -32002, update your code.

6Extensions Framework

Extensions existed informally before. Now they have a formal process. Extensions are identified by reverse-DNS IDs, negotiated through an extensions map, and live in their own repositories with delegated maintainers — versioning independently of the core spec. This lets the team test features in extensions before baking them into the protocol.

Two official extensions ship with this release:

  • MCP Apps — servers can deliver interactive HTML/JS interfaces that hosts render in a sandboxed iframe. Instead of just returning text or an image, an MCP server can now present a full UI.
  • Tasks — a stateless model for long-running operations. A server responds to tools/call with a task handle, and the client drives it using tasks/get, tasks/update, and tasks/cancel.

As Den Delimarsky (Anthropic) explained: "Extensions are a model for us to really test out things in the protocol before we bake them into the protocol."

What the Wire Looks Like Now

For developers, the most concrete change is what a request actually looks like on the wire. Here's a simplified before/after.

Before (2025-11-25 spec) — Stateful

// Step 1: initialize handshake
POST /mcp
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "clientInfo": { "name": "my-app", "version": "1.0" },
    "capabilities": { "roots": { "listChanged": true } }
  }
}
// Server responds with: { "sessionId": "abc-123", ... }

// Step 2: every subsequent call needs the session ID header
POST /mcp
Header: Mcp-Session-Id: abc-123
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "search", "arguments": { "q": "hello" } }
}

After (2026-07-28 spec) — Stateless

// No handshake. Just call the tool directly.
POST /mcp
Header: Mcp-Method: tools/call
Header: Mcp-Name: search
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "hello" }
  },
  "_meta": {
    "protocolVersion": "2026-07-28",
    "clientInfo": { "name": "my-app", "version": "1.0" },
    "capabilities": {}
  }
}
// Any server instance can handle this. No session needed.

The Mcp-Method and Mcp-Name headers let a load balancer route this to any available server without inspecting the JSON body. The _meta block carries everything the server needs to know about the client — replacing what the handshake used to establish.

Migration: Three Paths, Three Pain Levels

How much work this is for you depends entirely on how you built your MCP integration. There are three distinct paths.

Your migration effort scales with how far you strayed from the official SDKs.

Path A: You Used the Official SDK (Easy — Hours)

If you built on the official Python, TypeScript, Go, or C# SDKs without heavy modification, you're in good shape. The SDK abstracts away the stateless transition.

  • Update to the beta SDK (available now — see below)
  • Run your existing test suite
  • For Python v2: rename FastMCP to MCPServer (the decorator API is unchanged)
  • Pin an upper bound on dependencies: mcp<2 so the stable v2 release doesn't surprise you

Path B: You Forked or Extended an SDK (Medium — Days)

If you added custom middleware, custom transports, or wrapped the SDK with your own abstractions, you need to audit and adapt.

  • Audit where you store or expect session IDs — remove those code paths
  • Add Mcp-Method header emission to your transport layer
  • Move capability declarations from initialize-time to _meta
  • If you used Sampling, replace those calls with direct LLM API integration

The 12-month deprecation window gives you runway. Don't panic, but do plan a sprint.

Path C: You Built a Custom Implementation (Hard — Weeks)

If you hand-rolled JSON-RPC without using any SDK, this is the hardest path. Parra was candid: "If you built your own implementation, it's going to be a lot of uplift to make this correct."

  • Remove initialize() entirely from your server
  • Implement _meta propagation on every request handler
  • Add Mcp-Method / Mcp-Name header parsing and validation
  • Implement MRTR for any flows that need human-in-the-loop confirmation
  • Implement OAuth 2.0 iss validation per RFC 9207
  • Support application_type in Dynamic Client Registration
The silver lining for everyone: New clients that speak 2026-07-28 fall back to the initialize handshake when they reach a server on or before 2025-11-25. Backward compatibility is preserved at the protocol level — existing servers don't break today or on July 28. But interoperability between the newest clients and the oldest servers is not guaranteed indefinitely.

Beta SDKs Available Now

  • Python v2 — renames FastMCP to MCPServer, keeps the decorator API
  • TypeScript v2 — splits the monolithic SDK into @modelcontextprotocol/server and @modelcontextprotocol/client; ESM-only
  • Go v1.7.0-pre.1 — 2026-07-28 support on the same module path
  • C# 2.0.0-preview.1 — ModelContextProtocol packages

If you publish a library that depends on the Python mcp package, add an upper bound now: mcp>=1.27,<2 so the stable v2 release doesn't break your downstream users.

The Ecosystem at the Inflection Point

The 2026-07-28 revision isn't just a technical update — it's the moment MCP graduates from "promising open standard" to "enterprise-grade infrastructure." The ecosystem is already responding.

MCP sits at the protocol layer between AI models and the world. The revision makes that layer operable at enterprise scale.

Who Benefits Most

Enterprise platform teams are the biggest winners. The stateless core means they can finally deploy MCP servers the way they deploy everything else — behind standard load balancers, across regions, with horizontal autoscaling. No sticky sessions, no shared session stores, no affinity gymnastics. As Stacklok CEO Craig McLuckie (co-creator of Kubernetes) noted: "The stateful nature of MCP was really a by-product of its origin. The broader AI community is now embracing MCP as a mechanism to allow enterprises to intermediate access to production systems."

Gateway and infrastructure startups like Arcade (which raised $60M in June) and Stacklok built their entire thesis around the prediction that MCP would need to become operable. The spec revision validates that bet. Routable headers mean L7 gateways can manage MCP traffic the same way they manage REST and gRPC — routing, rate-limiting, and applying policy without deep packet inspection.

Security and governance teams get the most meaningful upgrade. The OAuth 2.0 alignment and iss validation give them a unified control point to apply agent-aware policy — exactly what's needed before agents touch production data and systems. The mix-up attack mitigation is particularly important for MCP's one-client-to-many-servers topology.

Developers building agent UIs get the MCP Apps extension — servers can now deliver interactive HTML interfaces rendered in sandboxed iframes. This transforms MCP from a text-and-tool-call protocol into something that can deliver full application experiences.

Who's at Risk

Anyone running a custom or homebrew MCP implementation that bypassed the official SDKs. If you hand-rolled JSON-RPC because the early SDKs were too limiting, you're facing a significant rewrite. The spec team acknowledges this honestly — there's no magic migration path. But the 12-month deprecation window for removed features, combined with backward-compatible client fallback, means nothing breaks immediately. You have time, but the clock is ticking.

Practical Takeaways

Here's what you should actually do, depending on where you sit.

If you're an SDK user

  • This week: Install the beta SDK in a test environment and run your existing test suite against it
  • Before July 28: Pin mcp<2 (or the equivalent for your language) in any library you publish
  • If Python: Prepare for the FastMCP → MCPServer rename
  • If TypeScript: Prepare for the package split and ESM-only requirement

If you operate MCP servers at scale

  • Now: You can start planning to remove sticky session configuration from your load balancers once you migrate
  • Test: Verify your LB can route on Mcp-Method headers — this unlocks L7 routing without body parsing
  • Consider: Evaluating gateway platforms (Arcade, Stacklok) if you need centralized agent policy enforcement

If you built a custom implementation

  • Audit now: Map every place you create, store, or validate session IDs
  • Scope: Estimate the rewrite — it's likely weeks, not days
  • Consider: Whether migrating to the official SDK (even forked) is cheaper than maintaining a bespoke implementation through this transition

If you're evaluating MCP for a new project

  • Start on the beta SDKs — there's no reason to learn the old stateful model
  • Explore extensions — MCP Apps and Tasks are available now and solve real problems (interactive UIs, long-running operations)
  • Design for statelessness from day one — pass explicit handles for any cross-call state, don't assume session continuity

The Bigger Picture

The MCP revision is a microcosm of a larger truth about AI infrastructure in 2026: the models are moving fast, but the plumbing moves at the speed of standards-body consensus.

It's tempting to look at the breakneck pace of model releases — Claude Opus 5, GPT-5.6, Gemini 3, Kimi K3, all landing within months of each other — and assume everything in AI moves that fast. It doesn't. The protocols, the security models, the governance frameworks, the operational tooling — all of that moves deliberately, through committee, with backward compatibility as a first-class constraint.

The 2026-07-28 revision is MCP's coming-of-age moment. It's the revision where the protocol stops being a research project that happened to get adopted, and starts being infrastructure that's designed for the use cases it actually has. Two years of hard lessons — about scaling, about security, about what features earn their complexity — are baked into this spec.

For anyone building AI agents in 2026, MCP is not optional infrastructure. It's the layer between your model and the world. Getting it right — stateless, secure, operable — is the difference between agents that demo well and agents that run in production. The July 28 revision is the moment that gap starts closing.

The spec goes final July 28, 2026. The beta SDKs are available now. There's no reason to wait.
